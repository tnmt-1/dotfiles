# Design Document（設計書）

## When to use

The user says 「設計書を書いて」「design document」「アーキテクチャ設計」「方式設計」— and the document covers **why** a system is built a certain way, spanning multiple design decisions.

## Relationship with ADR

| 種別 | 対象 | ファイル |
|------|------|---------|
| ADR | 1判断ごとの詳細（選択肢比較・トレードオフ） | `docs/adr/NNN-xxx.md` |
| 設計書 | 複数判断を束ねた全体設計 | `docs/researches/` またはプロジェクト任意の場所 |

設計書の中の「設計判断ログ」にサマリーを書き、詳細なトレードオフはADRへリンクする。

## Process

### 1. 企画

- **背景**: なぜこの設計が必要か
- **決定事項と未決定事項**: この設計書で何を決め、何を決めないか
- **読者**: 実装チーム／レビューア／運用担当者

### 2. アウトライン

```
## 概要
## 現状の課題
  - 現状の構成と問題点
  - 問題が顕在化している具体的ケース
## 設計方針
  - 設計の指針（変更の局所化、互換性維持など）
  - 採用しなかった選択肢の一覧（＋ADRへのリンク）
## アーキテクチャ
  - コンテキスト図
  - コンポーネント図（内部構造と他サービス依存）
## 処理フロー
  ### 正常系（Mermaidシーケンス図）
  ### 異常系（Mermaidシーケンス図）
## データ構造
  - 新規／変更するモデルとフィールド
  - スキーマ定義へのリンク
## 考慮事項
  ### パフォーマンス（想定QPS・レイテンシ目標）
  ### セキュリティ（認証境界・データ機密性）
  ### 運用（デプロイ順序・ロールバック・監視）
  ### テスト計画（UT/結合/E2Eの範囲）
## 設計判断ログ
  | 判断 | 選択肢 | 決定 | 理由 | 詳細ADR |
## 関連資料
```

### 3. 段落

パラグラフライティングを各セクションに適用:

1. **主題文**: 段落の核を1文で
2. **展開文**: 理由・具体例・データ（3-4個）
3. **結語文**: まとめ（省略可）

### 4. 文

- **異常系のシーケンス図は必ず書く**。設計の抜けがここで見つかる
- 選択肢は少なくとも2つ比較する。1つしかないなら設計判断ではない

## 考慮事項の取捨選択

すべて書く必要はない。この設計に関係あるものだけ残す。

| 項目 | 含める条件 |
|------|-----------|
| パフォーマンス | QPSが増える、新規外部I/Oが増える |
| セキュリティ | 新規データ項目、外部公開APIが増える |
| 運用 | デプロイ順序がある、ロールバック手順が特殊 |
| テスト計画 | 結合テストやE2Eに影響がある |

## 設計判断の書き方

各判断を表にまとめる:

| ID | 判断 | 選択肢 | 決定 | 理由 |
|----|------|--------|------|------|
| 1 | 採用DB | PostgreSQL vs MySQL vs DynamoDB | PostgreSQL | チーム習熟度が高く既存構成と統一できる |
| 2 | テーブル設計 | 新規テーブル vs 既存テーブル拡張 | 新規テーブル | 独立性が高く、既存に影響を与えない |

トレードオフの詳細な検討が必要な判断は `docs/adr/` に独立したADRを作り、「詳細ADR」列からリンクする。

## Verification

- 各セクションに1つ以上の段落があるか
- 異常系のフローが書かれているか
- 未決定の判断は「未解決課題」として明示されているか
- Mermaid図が構文エラーなくレンダリングされること
- ADRへのリンクが正しいパスを指していること

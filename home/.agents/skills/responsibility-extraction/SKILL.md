# 責務の切り出しリファクタリング

## このスキルが埋める溝

良い切り出しを見れば「うまい」と分かるが、自分ではどこに境界を引けばよいか言葉にできない。
そういう読者に向けて、このスキルは 2 つのものを返す。

1. 切り出し後のコード（差分）
2. 境界をそこに引いた理由の言語化

2 が無いと、読者は次の似た場面で再現できないし、出てきた差分の良し悪しも判断できない。
説明は「凝集度が高い」「SRP に従った」のような抽象語で済ませず、
コードの具体的な兆候（どの引数がどの関数に並んでいたか）と結びつけて書く。

## 手順

### 1. 読む — コードが暗黙に持っている「主語」を探す

切り出すべき責務は、たいてい既にコードの中に痕跡を残している。
まず以下の兆候を、根拠となる行番号つきで列挙する。grep で機械的に拾えるものが多い。

- 引数の塊（parameter clump）
  同じ引数の組み合わせが複数の関数に並んでいる。その組み合わせは、ひとつのオブジェクトの状態である。
  特に「ID を受け取り、毎回同じレコードを fetch してから本題に入る」関数が複数あれば、
  fetch 済みのオブジェクトを保持するクラスの候補と考える。
- 冒頭で繰り返される同じ分岐
  `if not config.feature_enabled: return default` のような早期 return が多くの関数の 1 行目にある。
  同じ判断を同じ主体が繰り返しているので、その主体を self に持てば分岐は 1 つの property になる。
- 関数名の修飾語
  `filter_terms_for_response` / `filter_terms_for_consent_check` の `for_〜` や、
  `evaluate_〜_enable` の共通接頭辞は、「誰が・どの場面で」判断するのかを名前で補っている。
  名前で補っているものは、クラスにすれば型で表せる。
- 作者が置いたセクション区切り
  `# ─── 管理画面事前条件 ───` のような見出しコメントは、作者がすでに感じている境界。尊重して持ち込む。
- 呼び出し側（serializer / controller / handler）に漏れたドメイン計算
  集合の差、ID リストの結合、クエリの組み立て、ループでの突き合わせ、結果同士を ID で結合して返却値を組み立てる処理。
  HTTP 層に残すべきなのは「入力を取り出す」「取得失敗をエラーにする」「ドメインの結果を見てエラーを投げるか返す」の 3 つだけ。
  クエリ回数を変えずに移せるなら、返却値の組み立てもドメイン側のメソッドにする。
- 別の場所に置かれた、この文脈の判定
  models や utils にある自由関数で、実際にはこの文脈の判断にしか使われないもの。

### 2. 主語を決める — 境界は「誰が判断するか」で引く

兆候から候補となる主語を決め、クラスの名前・保持する状態・判断する内容を書き出す。

- 技術的な役割名（Service、Manager、Helper、Util、Handler）ではなく、ドメインの階層や場面で名づける。
  「組織レベルの判定」「テナントレベルの判定」「1 回の同意評価」のように、
  読者がその名前を聞いただけで「どの情報を使って何を決めるか」を想像できる名前にする。
- 判断に必要な情報の範囲で階層を分ける。
  組織の設定だけで決まる判断は組織のクラスに、テナントの状態も要る判断はテナントのクラスに置く。
  下位の主語が上位の情報を使うなら、下位クラスが上位クラスのインスタンスを保持する（合成）。
  上位が下位のインスタンスを保持する向きの依存は作らない。
  ただし「配下のテナントに 1 件でも割当があるか」のように、上位が下位の集合を数える判断は上位のもの。
  その場合は下位クラスの状態を持たないクラスメソッド（`TenantRule.is_country_attribute_assigned_by_id(id)`）だけを呼び、
  下位のインスタンスは作らない。判断の定義を 1 箇所に保つための例外だと分かるようにしておく。
- 一連の関数が同じ 4〜6 個の入力を持ち回しているなら、それは「その処理の 1 回分」を表すオブジェクト。
  コンストラクタで入力を受け取り、公開メソッドを 1 つ、残りをプライベートなステップにする。
  ステップ間で渡していた引数は self に載る。
- 呼び出し側で「計算結果の集合を作る → そこから差分を出してエラー判定 → 同じ集合で再クエリ」
  という流れがあれば、計算済みの集合を保持する不変の値オブジェクトにし、
  差分などの導出値は property にする。呼び出し側にはエラーを投げる判断だけ残す。
- ID から fetch して始める入口は、`from_<id>()` のようなファクトリと、
  fetch なしで使える `〜_by_id()` クラスメソッドの両方を用意する。既存呼び出し側の負担を増やさない。
- 境界に迷ったら仮置きし、迷いをコメントに残す（「〜と統合できるかもしれない」）。
  分からないことを分からないまま可視化するほうが、無理に一本化するより次の人に優しい。

兆候と切り出し先の対応を、目安として一覧にしておく。

| 兆候 | 切り出し先 |
| --- | --- |
| ほぼ全関数が同じ X を受け取る | X を保持する Rule / Policy クラス |
| X に加えて Y も受け取る関数群がある | Y のクラスが X のクラスを保持する |
| 同じ 4〜6 個の入力を持ち回す関数の連鎖 | その処理 1 回分を表す Evaluation / Calculation クラス |
| 呼び出し側で集合計算 → エラー → 再クエリ | 計算済み集合を持つ不変の値オブジェクト |
| ID から毎回同じ fetch | `from_<id>()` ファクトリ + `〜_by_id()` クラスメソッド |
| 引数 1 つの純粋な変換 | 自由関数のまま残す |

### 3. 移す — 引数が減ることを確認する

関数をメソッドに移すとき、self に載った状態の分だけ引数が減っているはずである。
減っていないなら、切り出し先の主語が違う。これが最も手軽な検算になる。

- 自由関数として残してよいのは、引数 1 つの純粋な変換や、複数クラスから共有される小さな部品。
  すべてをクラスに入れることが目的ではない。
- 外から呼ばれないステップは private にする。
- モジュールにあったセクション見出しは、クラスの中にそのまま持ち込む。
  ファイル内の並びは「型定義 → 上位クラス → 下位クラス → 共有の自由関数 → 互換ラッパー」。
- 呼び出し側が実際に使うメソッドだけを要求する Protocol / interface を切り、具象型への依存を避ける。
- docstring やコメントは移動先に持っていき、self に載った引数の説明だけ削る。
  性能上の割り切り（N+1 を許容している理由など）を書いたコメントは必ず残す。

### 4. つなぐ — 旧 API を残して委譲する

一度にすべての呼び出し側を書き換えない。壊れる範囲を 1 コミットで把握できる大きさに抑える。

- 元のモジュール関数はすべて残し、中身を `Klass(...).method(...)` への 1 行の委譲にする。
  `# 互換用` のような印をつけ、後で消す対象だと分かるようにする。
  引数の個数・順序・型・戻り値の型も変えない。未使用の引数を削るのも、呼び出し側を壊すので別コミットにする。
- `_` 付きの非公開関数は、テストが直接 import していなければ消してよい。テストが見える環境では grep してから決める。
- 呼び出し側は 1 箇所ずつ新しい API に移す。旧関数は呼び出し元が 0 になった時点で、別コミットで消す。
- 既存テストは無変更で通す。新しいクラスに対するテストを追加する。
- 小さなモジュールが新クラスの部品になるなら吸収し、import 元を書き換える。

### 5. 検証する

- 既存テストが無変更で通ること（互換ラッパーがあるので通るはず）。走らせられない環境なら、その旨を明記する。
- 分岐条件・エラーメッセージ・発行クエリが前後で同じであること。振る舞いの変更は混ぜない。
- 各関数の引数数の前後を手元で表にして検算する。減っていることが切り出しの妥当性の根拠になる。表は説明に載せず、聞かれたら出す。

## 出力形式 — 説明は骨子だけにする

読者が知りたいのは「どういう考えのもと、どうしたか」であって、作業の記録ではない。
説明は見出しと要点だけで完結させ、細部は読者が指定したときにだけ広げる。
手順 1 で集めた兆候の一覧や行番号、関数ごとの引数表は、説明に書かず手元に残しておく。
読者が「なぜここを分けた」「この関数はどこへ行った」と聞いたときに、その根拠として出す。

`skeleton-doc-writing` スキルが使える環境なら、説明を書く前に Skill ツールで呼び出し、その規範に従う。
使えない環境でも、以下の要点は同じ。

- 見出しは 4 つまで。「考え方」「引いた境界」「変えていないこと」「残した迷い」を基本にし、不要なものは省く。
- 各見出しの下は箇条書き 1〜3 行。「引いた境界」だけはクラスの数だけ行を置いてよい。1 行に主張は 1 つ。見出しの言い換えだけの行は置かない。
- 「考え方」は、見つけた兆候から引き出した原則を書く。
  「`user_pool` しか見ない判断と、テナントの割当状態まで見る判断が混ざっていたので、判断に要る情報の範囲で 2 層に分けた」のように、
  兆候と原則を 1 行でつなぐ。行番号の羅列はしない。
- 「引いた境界」は、クラス 1 つにつき 1 行。「名前 — 保持するもの — 決めること」の形にし、理由は原則から自明でない場合だけ添える。
- 「凝集度」「単一責任」「保守性」といった抽象語は使わない。コードの具体に置き換える。
- 説明全体はコードを除いて 20 行前後、多くても 30 行に収める。それを超えるなら、細部を削るか読者の質問に回す。
- 呼び出し側に意図的に残した判断（結果を見て投げるだけのループなど）があれば、「残した迷い」に 1 行で書く。読者が「なぜこれは移さなかったのか」と迷わないようにする。
- 説明のあとに差分または新しいファイル全文を置く。コードの中のコメントは、説明で削った理由を補う場所ではない。移動元のコメントを保ち、新しい迷いだけを TODO として足す。

説明の例（Django のケースの場合）:

```markdown
## 考え方
- ほぼ全関数が user_pool を受け取り、一部はさらに user_pool_child_id を受け取っていたので、判断に要る情報の範囲で組織／テナントの 2 層に分けた
- 同意検証の 3 関数が同じ 5 つの入力を持ち回していたので、「同意検証 1 回分」をオブジェクトにした
- シリアライザにあった規約 ID の集合計算は、HTTP と無関係なので値オブジェクトへ移した

## 引いた境界
- OrganizationRule(user_pool) — 組織の設定だけで決まる判断（日本相当か、国機能が有効か、ユーザーの国の解決）
- TenantRule(user_pool_child) — OrganizationRule を保持し、テナントの属性割当状態を要する判断
- ConsentEvaluation(...) — 同意検証 1 回分。公開メソッド 1 つ、ステップは引数なし
- ConsentEvaluationPreparation — テナントで使える規約 ID の集合と、リクエストとの差集合

## 変えていないこと
- 旧関数はすべて `# 互換用` の 1 行委譲で残し、既存テストは無変更で通る
- N+1 と exists() の割り切りは元のまま。コメントも保った

## 残した迷い
- filter_terms_for_consent_check は ConsentEvaluation に統合できるかもしれない。呼び出し側の移行後に判断する
```

## やらないこと

- 振る舞いの変更や性能改善を同時にやらない。同じ N+1 は同じ N+1 のまま、コメントも保つ。
- 抽象基底クラスやインターフェースを先回りして作らない。実装が 1 つしかないものに抽象は要らない。
- メソッドが 1 つしかないクラスを作らない（公開 1 つ + private ステップ複数の Evaluation クラスは除く）。
- Service / Manager / Helper / Util という命名。
- 「凝集度」「単一責任」といった抽象語だけで理由を済ませること。

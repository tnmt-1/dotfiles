# 責務の切り出しリファクタリング

## このスキルが埋める溝

良い切り出しを見れば「うまい」と分かるが、自分ではどこに境界を引けばよいか言葉にできない。
そういう読者に向けて、このスキルは2つのものを返す。

1. 切り出し後のコード（差分）
2. 境界をそこに引いた理由の言語化

2が無いと、読者は次の似た場面で再現できないし、出てきた差分の良し悪しも判断できない。
説明は「凝集度が高い」「SRPに従った」のような抽象語で済ませず、
コードの具体的な兆候（どの引数がどの関数に並んでいたか）と結びつけて書く。

## 手順

### 0. 前提を確かめる — 呼び出し側とテストを変えてよいか

手順4の互換用の委譲は、既存の呼び出し側を壊さないためにある。最初に、守る対象があるかを確かめる。

- 対象のコードがリリース済みか、ほかのモジュールやリポジトリーから呼ばれているかを、呼び出し元のgrepとブランチの状態で確かめる。分からなければユーザーに聞く。
- 呼び出し側とテストを変えてよいなら、互換用の委譲は作らない。関数の削除、戻り値の型の変更、コンストラクタの引数の変更も候補に入れ、テストは新しい構造に合わせて書き直す。
- 候補を前提で絞るのは、兆候を集めたあとにする。守る対象があっても、見つけた兆候は「残した迷い」に書く。
- 触ってよいファイルをここで確定する。切り出し元のモジュール、grepで見つけた呼び出し側、そのテスト、手順4で吸収する小さなモジュールだけである。作業中にほかのファイルの兆候に気づいても、直さず「残した迷い」に書く。
- コードを変更する前に、手順5で使うテストの失敗一覧を記録する。

### 1. 読む — コードが暗黙に持っている「主語」を探す

切り出すべき責務は、たいていすでにコードの中に痕跡を残している。
まず以下の兆候を、根拠となる行番号つきで列挙する。grepで機械的に拾えるものが多い。

- 引数の塊（parameter clump）
  同じ引数の組み合わせが複数の関数に並んでいる。その組み合わせは、ひとつのオブジェクトの状態である。
  特に「IDを受け取り、毎回同じレコードをfetchしてから本題に入る」関数が複数あれば、
  fetch済みのオブジェクトを保持するクラスの候補と考える。
- 冒頭で繰り返される同じ分岐
  `if not config.feature_enabled: return default`のような早期returnが多くの関数の1行目にある。
  同じ判断を同じ主体が繰り返しているので、その主体をselfに持てば分岐は1つのpropertyになる。
- 関数名の修飾語
  `filter_terms_for_response` / `filter_terms_for_consent_check`の`for_〜`や、
  `evaluate_〜_enable`の共通接頭辞は、「誰が・どの場面で」判断するのかを名前で補っている。
  名前で補っているものは、クラスにすれば型で表せる。
  変数名やプロパティ名も同じである。`one_manga_recipients`と`two_manga_recipients`のように、番号を名前で表した組がある。タプルの位置で意味を分けた戻り値もある。
  どちらも、番号をキーにした辞書か、番号を受け取るメソッド（`mail_id_for(manga_count)`）にできる。
- 作者が置いたセクション区切り
  `# ─── 管理画面事前条件 ───`のような見出しコメントは、作者がすでに感じている境界である。尊重して持ち込む。
- 呼び出し側（serializer / controller / handler）に漏れたドメイン計算
  集合の差、IDリストの結合、クエリの組み立て、ループでの突き合わせ、結果同士をIDで結合して返却値を組み立てる処理。
  HTTP層に残すべきなのは「入力を取りだす」「取得失敗をエラーにする」「ドメインの結果を見てエラーを投げるか返す」の3つだけである。
  クエリ回数を変えずに移せるなら、返却値の組み立てもドメイン側のメソッドにする。
- 別の場所に置かれた、この文脈の判定
  modelsやutilsにある自由関数で、実際にはこの文脈の判断にしか使われないもの。
- 判定と応答が混ざった関数
  判定の途中で例外を送出し、ログレベルを選び、HTTPステータスを決めている。
  同じ判定を別の場面で使おうとすると、応答の違いが邪魔をして再利用できない。
- 散らばった保存形式の組み立て
  キャッシュのキーのプレフィックス、JSONへの変換と復元、保存先のパスやテーブル名の組み立てが、複数の関数に同じ形で現れる。
- 引き回される実行条件
  期限、タイムアウト、再実行の上限が、引数で何段も渡されている。
  インフラの制約から来た数字（タスクの制限時間など）が、処理の中に直接書かれている場合も同じである。
- 散らばった状態の更新
  同じレコードの状態を、複数の関数がそれぞれの条件で書き換えている。
- 検査した値を捨て、元のオブジェクトから組み直している
  検査するクラスが元のオブジェクト（モデルのインスタンスなど）をそのまま持ち、後の処理が同じ項目をそこから読み直している。
  同じ元から、別の場所でもう一度値を組み立てている場合も同じである。
- ほかのクラスの内部データを読んでいる
  あるクラスのメソッドが、別のクラスが持つ辞書やリストを直接引いて判断している。その判断は、データを持つクラスのものである。
- クラスの状態と同じ引数を受け取る自由関数
  既存のクラスのメソッドが、自分の属性をそのまま自由関数へ渡している。その自由関数は、クラスのプライベートなメソッドにできる。
- ログにしか使わない引数
  コンストラクタや関数の引数のうち、処理には使わず、ログの項目に出すだけのものがある。どの実行かを示す文脈（テナントID、日付など）が多い。

### 2. 主語を決める — 境界は「誰が判断するか」で引く

兆候から候補となる主語を決め、クラスの名前・保持する状態・判断する内容を書き出す。

- 技術的な役割名（Service、Manager、Helper、Util、Handler）ではなく、ドメインの階層や場面で名づける。
  たとえば「組織レベルの判定」「テナントレベルの判定」「1回の同意評価」のように、
  読者がその名前を聞いただけで「どの情報を使って何を決めるか」を想像できる名前にする。
- 判断に必要な情報の範囲で階層を分ける。
  組織の設定だけで決まる判断は組織のクラスに、テナントの状態も要る判断はテナントのクラスに置く。
  下位の主語が上位の情報を使うなら、下位クラスが上位クラスのインスタンスを保持する（合成）。
  上位が下位のインスタンスを保持する向きの依存は作らない。
  ただし「配下のテナントに1件でも割当があるか」のように、上位が下位の集合を数える判断は上位のものである。
  その場合は下位のインスタンスを作らず、状態を持たない下位クラスのクラスメソッド（`TenantRule.is_country_attribute_assigned_by_id(id)`）だけを呼ぶ。判断の定義を1箇所に保つための例外だと分かるようにしておく。
- 一連の関数が同じ4〜6個の入力を持ち回しているなら、それは「その処理の1回分」を表すオブジェクトである。
  コンストラクタで入力を受け取り、公開メソッドを1つ、残りをプライベートなステップにする。
  ステップ間で渡していた引数はselfに載る。
  設定、外部クライアント、接続といった依存は、入力とは分けてコンストラクタの後半で組み立てる。
  selfに載せるのは、コンストラクタで決まる入力と依存だけにする。
  ステップの途中で決まる値は、戻り値と引数で次のステップへ渡す。
- 判定と応答が混ざっていたら、判定を受け持つ型は真偽値か、結果の値オブジェクト（`can_enable`と`disabled_reason`を持つものなど）を返すだけにする。
  例外の種類、ログレベル、HTTPステータスは、処理の入口（エントリポイント）でまとめて決める。
  外部APIのクライアントも同じで、失敗は1種類の例外に外部のエラーコードを載せて送出し、業務上の例外への変換は呼び出し側に任せる。
- 保存形式の組み立てが散らばっていたら、保存する値を不変の値オブジェクトにし、キーと値への変換（`encode_key` / `encode_value` / `decode_value`）をそのクラスに置く。
  状態を変えるメソッドは、新しいインスタンスを返す。
- 同じ保存先の解決を繰り返していたら、`from_<元>()`で一度だけ解決する「所在」の値オブジェクトにし、保存先ごとの名前はpropertyにする。
  件数の取得と削除のように同じ対象を扱う処理が、同じ解決結果を使うようになる。
- 実行条件を引き回していたら、開始時刻、期限、上限を持つ不変の値オブジェクトにし、期限のような導出値はpropertyにする。
  インフラの制約から来た数字は入口（管理コマンドなど）だけに置き、導いた値をこのオブジェクトで渡す。
- 状態の更新が散らばっていたら、遷移ごとに1メソッドを持つ型に集める。
  遷移元の状態を条件に更新し、条件が崩れていたら専用の例外を送出する。
  この型は状態の変え方だけを知り、処理の中身（何をどう消すかなど）は知らない。
- 検査した値を捨てていたら、`from_<元>()`で検査して必要な値だけを取りだす不変の型にする。
  元のオブジェクトは持たず、後の処理にはこの型を渡す。同じ値の組み立ては、このファクトリだけにする。
- ログにしか使わない引数があれば、クラスは件数などの事実を戻り値で返し、どの実行かを示す文脈は入口でログに付ける。
  判定と応答を分け、例外やログレベルを入口で決めるのと同じ分け方である。
  処理にも使う値は、クラスの中のログに出してよい。
- 呼び出し側で「計算結果の集合を作る → そこから差分を出してエラー判定 → 同じ集合で再クエリ」
  という流れがあれば、計算済みの集合を保持する不変の値オブジェクトにする。
  差分などの導出値はpropertyにし、呼び出し側にはエラーを投げる判断だけ残す。
- IDからfetchして始める入口は、`from_<id>()`のようなファクトリと、
  fetchなしで使える`〜_by_id()`クラスメソッドの両方を用意する。既存の呼び出し側の負担を増やさない。
- 境界に迷ったら仮置きし、迷いをコメントに残す（「〜と統合できるかもしれない」）。
  分からないことを分からないまま可視化するほうが、無理に一本化するより次の人に優しい。

兆候と切り出し先の対応を、目安として一覧にしておく。

| 兆候 | 切り出し先 |
| --- | --- |
| ほぼ全関数が同じXを受け取る | Xを保持するRule / Policyクラス |
| Xに加えてYも受け取る関数群がある | YのクラスがXのクラスを保持する |
| 同じ4〜6個の入力を持ち回す関数の連鎖 | その処理1回分を表すEvaluation / Calculationクラス |
| 呼び出し側で集合計算 → エラー → 再クエリ | 計算済み集合を持つ不変の値オブジェクト |
| IDから毎回同じfetch | `from_<id>()`ファクトリ + `〜_by_id()`クラスメソッド |
| 判定の途中で例外・ログ・ステータスを決めている | 真偽値か結果を返す判定の型 + 応答を決めるエントリポイント |
| キーやJSONの組み立てが複数箇所にある | 保存形式への変換を持つ不変の値オブジェクト |
| 同じ保存先の解決を繰り返す | `from_<元>()`で一度だけ解決する所在の値オブジェクト |
| 期限や上限を引き回す | 実行条件を持つ不変の値オブジェクト |
| 同じレコードの状態を複数の関数が書き換える | 遷移ごとに1メソッドを持つ状態遷移の型 |
| 番号を名前で表した変数の組やタプルの位置 | 番号をキーにした辞書か、番号を受け取るメソッド |
| 検査した値を捨て、元から組み直す | `from_<元>()`で検査した値だけを持つ不変の型 |
| ほかのクラスの内部データを読んで判断する | データを持つクラスのメソッド |
| クラスの状態と同じ引数を受け取る自由関数 | そのクラスのプライベートなメソッド |
| ログにしか使わない引数 | 事実を返す戻り値と、文脈を付けてログを出す入口 |
| 引数1つの純粋な変換 | 自由関数のまま残す |

### 3. 移す — 引数が減ることを確認する

関数をメソッドに移すとき、selfに載った状態の分だけ引数が減っているはずである。
減っていないなら、切り出し先の主語が違う。これが最も手軽な検算になる。

- 自由関数として残してよいのは、引数1つの純粋な変換や、複数クラスから共有される小さな部品である。
  すべてをクラスに入れることが目的ではない。
- 外から呼ばれないステップはprivateにする。
- モジュールにあったセクション見出しは、クラスの中にそのまま持ち込む。
  ただし、見出しの語がその下の中身と合っているかは確かめ、合わなければ直す。
  ファイル内の並びは「型定義 → 上位クラス → 下位クラス → 共有の自由関数 → 互換ラッパー」とする。
- 呼び出し側が実際に使うメソッドだけを要求するProtocol / interfaceを切り、具象型への依存を避ける。
- docstringやコメントは移動先に持っていき、selfに載った引数の説明だけ削る。
  性能上の割り切り（N+1を許容している理由など）を書いたコメントは必ず残す。

### 4. つなぐ — 旧APIを残して委譲する

一度にすべての呼び出し側を書き換えない。壊れる範囲を1コミットで把握できる大きさに抑える。
この手順は、手順0で守る対象があると決めたときだけ使う。呼び出し側とテストを変えてよいときは、互換用の委譲を作らず、呼び出し側とテストを新しいAPIに直接書き換える。

- 元のモジュール関数はすべて残し、中身を`Klass(...).method(...)`への1行の委譲にする。
  `# 互換用`のような印をつけ、後で消す対象だと分かるようにする。
  引数の個数・順序・型・戻り値の型も変えない。未使用の引数を削るのも、呼び出し側を壊すので別コミットにする。
- `_`付きの非公開関数は、テストが直接importしていなければ消してよい。テストが見える環境ではgrepしてから決める。
- 呼び出し側は1箇所ずつ新しいAPIに移す。旧関数は呼び出し元が0になった時点で、別コミットで消す。
- 既存テストは無変更で通す。新しいクラスに対するテストを追加する。
- 小さなモジュールが新クラスの部品になるなら吸収し、import元を書き換える。

### 5. 検証する

次のコマンドで、振る舞いが変わっていないことを確かめる。`<分岐元>`は切り出しを始める前の変更IDかbookmark名（多くは`trunk()`）に置き換える。

1. 手順0で記録したときと同じテストコマンドで失敗一覧を取り、新しい失敗が0件であることを確認する。Pythonでは`~/.pi/agent/skills/python/scripts/test_failures.sh`を使う（使い方は`python`スキルの「検証と自己修復」）。ほかの言語では、プロジェクトのテストコマンドが出す失敗テスト名を前後でファイルに保存し、`comm -13`で比べる。
2. 互換用の委譲を残したときは、既存のテストファイルから削除・変更した行が0行であることを確認する。新しいテストの追加は数えない。
   ```bash
   jj diff --git --from '<分岐元>' | awk '/^diff --git/ { f = $NF } /^-[^-]/ && f ~ /test/ { print f ": " $0 }'   # 出力が空なら合格
   ```
3. 差分に逃げ道が入っていないことを確認する。移動した行は削除側にも同じ行があるので、数えられない。
   ```bash
   jj diff --git --from '<分岐元>' | ~/.pi/agent/skills/python/scripts/diff_guard.sh   # 終了コード0なら合格
   ```

どれかが失敗したら、次のループで直す。

1. 失敗したテストの最初のエラーを読み、どの移動で分岐条件、エラーメッセージ、発行クエリが変わったかを特定する。
2. 切り出した側のコードを直して、元の振る舞いに戻す。互換用の委譲を残したときは、既存テストを直して通さない。
3. 失敗したコマンドを再実行し、通ったら上の1からやり直す。

修正は、同じ検証につき3回までにする。3回で通らなければ止まり、失敗したコマンド、エラーの先頭10行、試した修正を報告する。切り出しを小さくして通すかどうかは、読者が決める。

コマンドで確かめられないものは、次の観点で読んで確かめる。

- 手順0でテストを書き直してよいと決めたときは、書き直したテストが同じ分岐、エラーメッセージ、発行クエリを確かめていること。
- 分岐条件・エラーメッセージ・発行クエリが前後で同じであること。振る舞いの変更は混ぜない。
- 各関数の引数数の前後を手元で表にして検算する。減っていることが切り出しの妥当性の根拠になる。表は説明に載せず、聞かれたら出す。
- 切り出したあとのコードに、手順1の兆候をもう一度当てる。切り出しで見通しがよくなり、初めて見える兆候がある。特に次を確かめる。
    - 各クラスと関数の引数が、ログ以外の処理に使われているか
    - クラスの状態と同じ引数を受け取る自由関数が残っていないか
    - クラスどうしが、互いの内部データを読んでいないか
    - セクション見出しの語が、その下の中身と合っているか

### 完了条件

次をすべて満たしたときだけ、切り出しが終わったと報告する。

- [ ] 手順5の1で、新しい失敗が0件。テストを実行できない環境では、完了としない。実行できなかった理由を書いて止まる。
- [ ] 互換用の委譲を残したときは、手順5の2の出力が空。
- [ ] 手順5の3の終了コードが0。
- [ ] 各関数の引数が切り出し前より減っている。減っていない関数は、主語を選び直すか「残した迷い」に書いた。
- [ ] 下の出力形式で骨子を書き、「変えていないこと」に手順5の実行結果を1行で書いた。

## 出力形式 — 説明は骨子だけにする

読者が知りたいのは「どういう考えのもと、どうしたか」であって、作業の記録ではない。
説明は見出しと要点だけで完結させ、細部は読者が指定したときにだけ広げる。
手順1で集めた兆候の一覧や行番号、関数ごとの引数表は、説明には書かず、手元に残しておく。
読者が「なぜここを分けた」「この関数はどこへ行った」と聞いたときに、その根拠として出す。

`kosshi`スキルが使える環境なら、説明を書く前にSkillツールで呼び出し、その規範に従う。
使えない環境でも、以下の要点は同じである。

- 見出しは4つまでにする。「考え方」「引いた境界」「変えていないこと」「残した迷い」を基本にし、不要なものは省く。
- 各見出しの下は箇条書きで1〜3行にする。「引いた境界」だけはクラスの数だけ行を置いてよい。1行には主張を1つだけ書く。見出しの言い換えだけの行は置かない。
- 「考え方」は、見つけた兆候から引き出した原則を書く。
  たとえば「`user_pool`しか見ない判断と、テナントの割当状態まで見る判断が混ざっていたので、判断に要る情報の範囲で2層に分けた」のように、
  兆候と原則を1行でつなぐ。行番号の羅列はしない。
- 「引いた境界」は、クラス1つにつき1行で書く。「名前 — 保持するもの — 決めること」の形にし、理由は原則から自明でない場合だけ添える。
- 「凝集度」「単一責任」「保守性」といった抽象語は使わない。コードの具体に置き換える。
- 説明全体はコードを除いて20行前後、多くても30行に収める。それを超えるなら、細部を削るか読者の質問に回す。
- 「変えていないこと」には、呼び出し側とテストを変えたかどうかを1行で書く。
- 呼び出し側に意図的に残した判断（結果を見て投げるだけのループなど）があれば、「残した迷い」に1行で書く。読者が「なぜこれは移さなかったのか」と迷わないようにする。
- 説明のあとに差分または新しいファイル全文を置く。コードの中のコメントは、説明で削った理由を補う場所ではない。移動元のコメントを保ち、新しい迷いだけをTODOとして足す。

Djangoのケースでは、説明は次のようになる。

```markdown
## 考え方
- ほぼ全関数が user_pool を受け取り、一部はさらに user_pool_child_id を受け取っていたので、判断に要る情報の範囲で組織／テナントの 2 層に分けた
- 同意検証の 3 関数が同じ 5 つの入力を持ち回していたので、「同意検証 1 回分」をオブジェクトにした
- シリアライザにあった規約 ID の集合計算は、HTTP と無関係なので値オブジェクトへ移した

## 引いた境界
- OrganizationRule(user_pool) — 組織の設定だけで決まる判断（日本相当か、国機能が有効か、ユーザーの国の解決）
- TenantRule(user_pool_child) — OrganizationRule を保持し、テナントの属性割当状態を要する判断
- ConsentEvaluation(...) — 同意検証 1 回分。公開メソッド 1 つ、ステップは引数なし
- ConsentEvaluationPreparation — テナントで使える規約 ID の集合と、リクエストとの差集合

## 変えていないこと
- 旧関数はすべて `# 互換用` の 1 行委譲で残し、既存テストは無変更で通る
- N+1 と exists() の割り切りは元のまま。コメントも保った

## 残した迷い
- filter_terms_for_consent_check は ConsentEvaluation に統合できるかもしれない。呼び出し側の移行後に判断する
```

## やらないこと

- 振る舞いの変更や性能改善を同時にやらない。同じN+1は同じN+1のまま、コメントも保つ。
- テストを弱めて通さない。既存テストの削除、skipやxfailの追加、assertの緩和をしない。手順0でテストを書き直してよいと決めたときも、確かめる分岐を減らさない。
- 「暫定」「一時的」「とりあえず」のような、切り出しの不完全さを言い訳するコメントを書かない。後で消す対象には`# 互換用`を付け、境界の迷いはTODOと「残した迷い」に書く。
- `# noqa`や`# type: ignore`を足して警告を黙らせない。移動元にあったものはそのまま持っていく。
- 手順0で確定したファイルのほかには触らない。
- 抽象基底クラスやインターフェースを先回りして作らない。実装が1つしかないものに抽象は要らない。
- メソッドが1つしかないクラスを作らない（公開1つ + privateステップ複数のEvaluationクラスは除く）。
- Service / Manager / Helper / Utilという命名。
- ステップの途中でselfに値を代入し、後のステップにその値があることを前提にさせること。呼び出し順への依存が生まれる。
- 「凝集度」「単一責任」といった抽象語だけで理由を済ませること。
- プロジェクトで使っていない設計手法の語（エンティティ、値オブジェクト、集約など）を、コメント、docstring、見出しに持ち込むこと。
  このスキルの本文の「値オブジェクト」は説明のための語である。コードの見出しには、言語の機能の名前（データクラス、例外）か、中身を書く。

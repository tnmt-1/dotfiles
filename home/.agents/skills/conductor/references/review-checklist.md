# 監視とレビューの観点

観点を増やすときはここに足す。SKILL.mdの手順は触らない。

## 判定の書き方

この文書の観点でレビューするときは、観点ごとに `合格` か `不合格: <理由>` を書く。
判断がつかない観点は不合格にし、何が分からないかを理由に書く。
最後の行には、すべて合格なら `判定: 合格`、1つでも不合格なら `判定: 不合格` と書く。
レビューを通すのは `判定: 合格` のときだけである。

## 監視中に止める兆候（手順5）

見えたら `Ctrl+C` で止め、修正指示を送るか指示書を書き直す。

- 担当範囲外のファイルを開いている、または編集している
- 計画にないファイルを作ろうとしている
- 同じエラーを繰り返している
- テストや静的検査を通すために、skip、`noqa`、`type: ignore` を足している。または既存テストの期待値を書き換えている
- 指示書の事前条件の外の入力や状態を扱う分岐、例外処理、既定値の補完を書いている
- テストのタスクが書いたテストや既存のテストを、実装のタスクが編集している
- 計画の「人の確認が要る変更」にない種類の変更（マイグレーション、権限、データの削除、外部への送信、依存パッケージ）をしている
- 承認待ち（piの `rm *` など）で止まったまま進まない

## テストのレビュー（conductorは手順7、soloistは手順2）

実装より先に書いたテストを、実装を始める前に確かめる。
テストを書いた担当は、追加したテストのIDを `<作業用ディレクトリ>/new-tests.txt` に1行1件で書き、完了条件の行との対応表を返している。

- `<作業用ディレクトリ>` は、soloistでは `.soloist/`、conductorでは `.conductor-tasks/` である。conductorでは、ファイル名にテストのタスクの番号を付ける（`new-tests-<n>.txt`、`red-<n>.txt`、`tests-<n>.sha`）
- `<テストのファイル>` は、テストを書く担当の指示書で「触ってよいファイル」に挙げたファイルである

次の観点で判定する。

- 完了条件のどの行にも、対応するテストがある
- テストが呼ぶ実装側の名前は、計画の「テストから呼ぶ名前」にあるものだけである
- 期待する出力が完了条件の表と同じである。拒否のケースでは、何も保存されないことまで確かめている
- 事前条件の外の入力を与えるテストがない
- テスト以外のファイルを変更していない
- 実装前に失敗する。次のコマンドで確かめる

    ```bash
    ~/.pi/agent/skills/python/scripts/test_failures.sh <作業用ディレクトリ>/red.txt poetry run pytest -q --tb=no --continue-on-collection-errors <テストのファイル>
    comm -23 <(sort -u <作業用ディレクトリ>/new-tests.txt) <(sed 's/^[A-Z]*:* //' <作業用ディレクトリ>/red.txt | sort -u)
    ```

    `comm` の出力は、実装前に失敗しなかったテストである。出力された行が次のどちらにも当たらなければ、不合格にする。
    - 完了条件で「（既存）」と書いた行のテスト
    - `red.txt` にファイル名だけで出たファイルのテスト。まだない名前をimportしているため、ファイルごと収集に失敗している

合格したら、テストのファイルのハッシュを記録する。実装のあとで、テストが変わっていないことを確かめるのに使う。

```bash
shasum <テストのファイル> > <作業用ディレクトリ>/tests.sha
```

## 差分レビュー（手順7）

```bash
jj diff
```

- 計画どおりか。勝手な追加や省略がないか
- 担当範囲外のファイルを触っていないか
- 完了条件のコマンドが実際に通るか。自分で実行して終了コードを見る
- `diff_guard.sh` の出力が空か（SKILL.md手順7）
- 既存テストを削除・緩和していないか。次のコマンドで既存テストの削除行を出し、一行ずつ理由を確かめる
    ```bash
    jj diff --git --from '<分岐元>' | awk '/^diff --git/ { f = $NF } /^-[^-]/ && f ~ /test/ { print f ": " $0 }'
    ```
- 全体のユニットテストで、手順1の記録になかった失敗が増えていないか
- 指示書に書いた規約（コミット粒度、最後のリファクタ、セルフレビュー）に沿っているか
- 手順6の指摘（`/ponytail-review` のdelete/stdlib/yagni、pythonスキルのレビュー、防御的実装のレビューの指摘）が直っているか。見送った指摘に理由が付いているか
- テストを書いた担当のテストが変わっていないか。`shasum -c <作業用ディレクトリ>/tests.sha` の終了コードが0になる
- 完了の報告の「完了条件とテスト」の表で、すべての行のテストが実装後に成功しているか
- 差分のうち人の確認が要る変更は、計画の一覧と一致しているか。ファイル名で拾えるものは次のコマンドで出し、出た行がすべて計画にあることを確かめる。権限、データの削除、外部への送信は差分を読んで確かめる
    ```bash
    jj diff --name-only --from '<分岐元>' | grep -E '(^|/)migrations/|pyproject\.toml|poetry\.lock'
    ```
- 事前条件の外のケースを扱うコードとテストがないか。観点は次の「防御的実装」の節
- 指示書で読ませたスキルの観点（例 `python` スキルのreferences）から逸脱していないか
- sekimuの切り出しタスクで委譲先が出した骨子（考え方、引いた境界、変えていないこと、残した迷い）と差分が合っているか。分岐条件、エラーメッセージ、発行クエリが前後で変わっていないか

## 防御的実装（手順6・7）

事前条件の外のケースを扱うコードは、テストが通るので、差分を読まないと見つからない。
計画の事前条件と事後条件を手元に置き、追加行を1つずつ次の順で判定する。

1. その分岐、補完、例外処理が扱うケースを、具体的な入力や状態で言う
2. そのケースが事前条件の下で起こりえないなら、削除する
3. 起こりうるのに計画のどこにも書かれていないケースなら、コードには手を付けず、計画の書き漏れとして報告する

拾う形は次のとおりである。

- 事前条件で必須のキーや属性を、`.get()`、`getattr()` の既定値、`hasattr()` で読む
- 型ヒントが `None` を含まない値への `is None` 判定や、`or ""`、`or []`、`or 0` での補完
- 型ヒントで決まっている値への `isinstance()` 判定
- Serializer、権限クラス、DB制約が保証した条件を、Serviceやモデルで確かめ直す
- 呼び出した処理の事後条件（戻り値の形、保存した状態）を、呼び出し側で確かめ直す
- 事前条件の下では送出されない例外を捕まえる `try`/`except`
- 事前条件の外の入力を与えるテスト

次は防御的実装に当たらない。

- 信頼境界での検証。リクエスト、外部APIの応答、ファイルを受け取る場所の検証は、事前条件を作る側である
- 欠損が仕様として残る値の `.get()`（pythonスキルの `references/common/api-design.md`）
- 完了条件に書いた業務上の拒否

ponytail-reviewやpythonスキルのレビューが、事前条件の外のケース（空、ゼロ、`None` など）を扱うよう指摘したら、その指摘は見送る。見送る理由には「事前条件の外」と書く。

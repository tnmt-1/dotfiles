# タスク指示書テンプレート

指示書は実装側が元の会話を一切知らない前提で書く。
`<agent-skills>` は `references/agents.md` のスキル置き場に置き換える（piなら `~/.pi/agent/skills`）。
`<ponytail-review-skill>` は `references/agents.md` にあるponytail-reviewのSKILL.mdの絶対パスに置き換える。

```markdown
# タスク: <一行で>

## 最初に読み込むスキル
<タスクに該当するものを名前で列挙する。読めなかった場合に備えて
 <agent-skills>/<name>/SKILL.md の絶対パスも併記する。~/.claude/skills/ のパスは書かない>
- Python の実装・修正: `python` スキル（<agent-skills>/python/SKILL.md）。
  SKILL.md の指示に従い references/ の該当文書（common/api-design.md, common/testing.md,
  django/implementation.md, django/testing.md など）まで読んでから実装する
- 日本語を書く作業すべて: `tenmaru` スキル
  （<agent-skills>/tenmaru/SKILL.md）。設計書や README だけでなく、docstring、コメント、
  テスト名、ログメッセージ、コミットメッセージの日本語もこのスキルに従って書く
- 責務の切り出しタスク: `sekimu` スキル（<agent-skills>/sekimu/SKILL.md）。
  境界の引き方に迷ったら references/worked-example.md も読む

## 背景
<この変更が必要な理由。周辺の設計上の制約>

## やること
1. <具体的な手順>

## 事前条件と事後条件
<計画から、このタスクで変更する処理の分を写す。事前条件には保証する場所も添える>

## 通すテスト
テストのタスクが先に書いたテスト。一覧は `<リポジトリの絶対パス>/.conductor-tasks/new-tests-<n>.txt` にある（`<n>` はテストのタスクの番号）。
このタスクではテストを書かず、編集もしない。

## 人の確認が要る変更
<計画から、このタスクの分を写す。なければ「なし」と書く>

## 規約（既定。変更指示がなければこのまま）
- 機能単位でコミットする（1機能 = 1コミット）
- 機能が一通り完成したら最後にリファクタリングし、1コミットにまとめる
- 各機能ごとにセルフレビューしてから次へ進む。観点は ponytail-review スキル（<ponytail-review-skill>）と、正しさ・セキュリティ・性能、防御的実装（<agent-skills>/conductor/references/review-checklist.md の「防御的実装」の節）。Python を変更したら python スキル（<agent-skills>/python/SKILL.md と該当する references/）の観点も加える
- テストは変更したファイルに関係するものだけを実行する。全体のユニットテストは監督側が実行するので、実行しない
- Git 操作は jj を使う（git を使う場合は理由を明示する）。分岐元と新規 bookmark 名、PR マージ先はユーザー指示に従う

## 禁止事項（変更しない）
- 「暫定」「一時的」「とりあえず」「workaround」のような、不完全さを言い訳するコメントを書かない。既知の制約は最後の報告に書く
- `# noqa`、`# type: ignore`、skip、xfail を足して検証を通さない
- 既存テストの期待値を、実装の出力に合わせて書き換えない
- 「触ってよいファイル」にないファイルを編集・作成しない。必要だと分かったら、編集せずに理由を書いて止まる
- 「事前条件と事後条件」の外の入力や状態を扱う分岐、例外処理、既定値の補完、テストを書かない。事前条件が実際には保証されていないと分かったら、扱うコードを書かずに理由を書いて止まる
- テストのファイルを編集・作成しない。テストが計画や仕様と食い違うと分かったら、テストを変えずに理由を書いて止まる
- 「人の確認が要る変更」にない種類の変更（マイグレーション、権限、データの削除、外部への送信、依存パッケージ）をしない。必要だと分かったら、変更せずに理由を書いて止まる

## 失敗したとき
完了条件のコマンドが失敗したら、最初のエラーを読んで原因を1つ直し、同じコマンドを再実行する。
同じコマンドの修正は3回までにする。修正のたびに、「通すテスト」の失敗件数を画面に出す。失敗件数が減らない修正が2回続いたときは、3回を待たずに止まる。
止まるときは、失敗したコマンド、エラーの先頭10行、試した修正を画面に出す。

## 触ってよいファイル
- path/to/a.py

## 触ってはいけないもの
- <他のセッションが担当する範囲>

## 完了条件
次のコマンドがすべて終了コード0になったら完了とする。完了したら、実行したコマンドと終了コードを画面に出す。
- `<通すテストのコマンド。例 poetry run pytest $(cat <リポジトリの絶対パス>/.conductor-tasks/new-tests-1.txt)>`
- `<変更したファイルに関係するテストのコマンド。例 poetry run pytest path/to/test_a.py>`
- `<静的検査のコマンド。例 poetry run pre-commit run --files path/to/a.py>`
- `jj diff --git --from '<分岐元>' | <agent-skills>/python/scripts/diff_guard.sh`
```

## sekimu の切り出しタスクで足すこと

SKILL.md手順1でsekimuの切り出しタスクを置いたときは、上のテンプレートに次を足す。

- 背景: sekimuの手順0の答えを書く。「呼び出し側とテストを新しいAPIに書き換えてよい」か「互換用の委譲を残し、既存テストは変えない」のどちらか。ユーザーには質問せず、この答えに従うよう書く
- やること: sekimuの手順に従って切り出す。分岐条件、エラーメッセージ、発行クエリは前後で変えない
- 規約: 既定規約のうち「最後にリファクタリングする」は省く。タスク自体がリファクタリングのため
- 触ってよいファイル: 切り出し元のモジュールに加え、書き換える呼び出し側とテストも列挙する
- 完了条件: sekimuの出力形式の骨子（考え方、引いた境界、変えていないこと、残した迷い）を最後に画面へ出す

## テストのタスクで足すこと

SKILL.md手順1で置いたテストのタスクでは、上のテンプレートを次のように変える。テストのタスクは、実装のタスクとは別のセッションで動かす。

- 背景: このタスクではテストだけを書き、実装は別のセッションが行うと書く。実装のセッションはこのテストを変えられないので、テストは計画の完了条件だけを根拠に書く
- 「通すテスト」の節の代わりに「テストの観点」の節を置き、計画の完了条件から、このタスクの分を写す。1行が1つのテストになる
    - 統合: <シナリオ>: <入力> → <期待する出力>
    - パラメーター: <パラメーター名>: <必須と任意の別、型・形式、長さ・範囲、選択肢>
    - 相関: <規則>
    - 業務ルール: <判定と、結果が変わる組み合わせ>
    - 既存テストの期待値の変更: <テストの名前と、変える理由>
- 「テストから呼ぶ名前」の節を置き、計画から写す
- やること:「テストの観点」の行ごとにテストを書く。実装側の名前は「テストから呼ぶ名前」にあるものだけを呼ぶ。追加したテストのIDを `<リポジトリの絶対パス>/.conductor-tasks/new-tests-<n>.txt` に1行1件で書く
- 規約: 既定規約のうち「最後にリファクタリングする」は省く。セルフレビューの観点は、pythonスキルの `references/common/testing.md` と、各フレームワークのtesting referenceにする
- 禁止事項: テスト以外のファイルを編集しない。実装も、実装の代わりになるスタブも書かない
- 触ってよいファイル: テストのファイルに加え、使うfactoryやconftestのファイルを列挙する
- 完了条件: 次の2つにする。実装前なのでテストは失敗し、終了コード0にはならない。失敗の確認は監督側が行う
    - テストのファイルに対する静的検査の終了コードが0。まだない名前を参照していることによる指摘だけは残してよい
    - 「テストの観点」の行とテストのIDの対応表を、画面に出す

## 完了条件の書き方

- 1行にコマンド1つを書き、「終了コード0」で合否が決まる形にする。「動くこと」「問題ないこと」のように、読んだ人の判断で合否が変わる書き方をしない
- 監督側が手順7で同じコマンドを自分で実行する。そのままコピーして実行できるように、置き場所を残さずに書く
- コマンドで確かめられない条件（画面の見た目など）は完了条件に入れず、監督側の差分レビューで確かめる
- テストのタスクは例外とする。完了条件と、監督側が行う失敗の確認は、上の「テストのタスクで足すこと」と `references/review-checklist.md` の「テストのレビュー」に従う

## 既定規約の意図

ユーザーが特段の指示をしなくても、委譲する実装はこの流れに従う。規約欄にそのまま書き込む。

- 機能単位でコミットを残す。1機能 = 1コミットを目安にし、無関係な変更を混ぜたり、途中経過をまとめたりしない
- 機能が一通り完成したら、最後にリファクタリングする。重複や不整合、読みづらい箇所を整えて1コミットにまとめる。整えるのは触ってよいファイルの中だけにする。クラスの切り出しのように触ってよいファイルを超える整理は、sekimuの切り出しタスクとして計画で切る（SKILL.md手順1）
- テストは、変更したファイルと関係するものに絞る。全体のユニットテストは時間がかかり、既存の失敗との見分けも要るため、監督側が実装前後に実行して比較する（SKILL.md手順1・7）
- 各機能ごとにセルフレビューする。差分を自分で読み、規約と計画からの逸脱、触ってはいけない範囲の混入、事前条件の外のケースを扱うコードを確認してから次の機能へ進む。観点は完了後に監督側が回す `/ponytail-review`、pythonスキル、防御的実装のレビュー（SKILL.md手順6）と同じにする。最後のレビューで指摘が山積みになるのを防ぐためである
- 実装のタスクではテストを書かない。テストのタスクが先に書いたテストを通す。実装する本人がテストを書くと、テストが実装に合わせて書かれ、計画ではなく実装を確かめるものになる（`references/plan-criteria.md`）

分岐元（大元）のブランチ、新規bookmark名、PRのマージ先は状況ごとにユーザーが指定するため、固定しない。委譲を始める前にユーザーへ確認する。

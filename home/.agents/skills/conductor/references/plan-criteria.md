# 計画に書く条件

SKILL.mdの手順1で、計画に次の4つを書くときに読む。

- 処理ごとの事前条件と事後条件。実装してよい範囲を決める
- 完了条件。何が確かめられたら完了とするかを決める
- テストから呼ぶ名前。実装より先にテストを書くために決める
- 人の確認が要る変更。テストが通っても人が差分を読む変更を決める

どれも指示書に写し、差分レビューの基準にする。

## ユーザーが承認するもの

ユーザーが承認するのは、上の4つである。コードの差分は承認の対象にしない。
ここで合意しておけば、完了したときに人が見るのは、完了の報告にある完了条件とテストの対応表と、人の確認が要る変更の差分だけになる。

承認のあとで4つのどれかを変えるときは、変える内容をユーザーに示し、承認を取り直してから反映する。
実装中やレビューで計画の書き漏れが見つかったときも、同じように扱う。

## 事前条件と事後条件

計画で変更する処理（エンドポイント、Serviceの公開メソッド、バッチなど）ごとに書く。

- 事前条件: 処理に入る時点で成り立っている入力と状態。条件ごとに、それを保証する場所を添える
- 事後条件: 処理が正常に終わった時点で成り立つこと。レスポンス、戻り値、保存されたデータ、外部への送信を書く

保証する場所は、Serializerの定義、認証・権限クラス、`get_queryset()` の絞り込み、DB制約、呼び出し元の処理などである。
保証する場所を挙げられない条件は、事前条件に書かない。
業務上の理由で拒否する入力（締切後の回答など）も事前条件ではない。処理が扱うケースとして、完了条件に書く。

実装では、事前条件を満たさない入力や状態を扱わない。分岐、例外処理、既定値での補完、テストのどれも書かない。
呼び出し側も、呼び出した処理の事後条件を確かめ直さない。

```markdown
| 処理 | 事前条件 | 保証する場所 |
| --- | --- | --- |
| `POST /forms/{form_id}/answers/` | フォームが存在し、リクエストしたユーザーのテナントに属する | View の `get_queryset()` のテナント絞り込み |
| 同上 | `answers` の各要素が `question_id` と `value` を持つ | `AnswerItemSerializer` の `required=True` |

| 処理 | 事後条件 |
| --- | --- |
| `POST /forms/{form_id}/answers/` | 回答が1件保存され、フォームの回答数が1増える |
```

## 完了条件

統合テストの観点、ユニットテストの観点、確かめるコマンドの3つを書く。
観点は、1行が1つのテストになる粒度で書く。
事前条件の外のケースは、どの観点にも書かない。

完了条件のテストは、実装より先に、実装しない担当が書く。テストを書く担当は、行ごとにテストを1つ書き、行とテストの対応を返す。
そのため、実装前には完了条件のテストがすべて失敗する。計画の時点ですでに満たされていると分かっている行には、末尾に「（既存）」と書く。実装前に成功してよいのは、この行のテストだけである。

仕様の変更で期待値が変わる既存のテストは、テストの名前と変える理由を完了条件に挙げる。このテストも、テストを書く担当が直す。

### 統合テストの観点

APIやバッチの入口から見て、ブラックボックスで書く。内部でどの関数を呼ぶかには触れず、入力と期待する出力だけを書く。
テストも入口（DRFならエンドポイント）を呼ぶ形で書く。
シナリオは「誰が、どの状態で、何をすると、どうなるか」を仕様の言葉で書く。`~/dev/cdm/` 配下なら、`cdm-notion` スキルで仕様を確かめてから書く。

次の3種類を含める。

- 業務の正常系: 仕様が想定する主な使い方
- 業務上の拒否: 締切後の回答、上限を超える登録など、仕様が拒否すると決めているケース
- 権限とテナント境界: 未認証、権限なし、他テナントのデータへのアクセスが拒否されること

期待する出力には、レスポンスに加えて、保存されたデータと外部への送信も書く。拒否のケースでは、何も保存されないことまで書く。

```markdown
| シナリオ | 入力（リクエストと事前の状態） | 期待する出力 |
| --- | --- | --- |
| 回答者が受付中のフォームに回答する | 受付中のフォーム。必須の設問すべてに値がある回答 | 201。回答が1件保存され、回答数が1増える |
| 回答者が締切後のフォームに回答する | 締切を過ぎたフォーム | 400。回答は保存されない |
| 他テナントのユーザーが回答する | 別のテナントに属するフォームのID | 404。回答は保存されない（既存） |
```

### ユニットテストの観点

少なめにする。書くのは次の3つだけである。

1. リクエストパラメーターのあるべき姿: パラメーターごとに、必須と任意の別、型と形式、長さや値の範囲、選択肢を書く。テストでは、必須の欠落と、範囲の境界の前・境界値・境界の後を確かめる。境界の取り方はpythonスキルの `references/common/testing.md` の「境界値」に従う
2. 相関チェック: 複数のパラメーターにまたがる規則を書く。規則ごとに、満たす組み合わせと満たさない組み合わせを1つずつ確かめる
3. 業務ルールの判定: Serviceや判定型の結果が、状態や区分の組み合わせで変わる場合に書く。統合テストで組み合わせを網羅すると件数が多くなりすぎるときだけ使い、統合テストで足りるなら書かない

```markdown
| パラメーター | 必須 | 型・形式 | 長さ・範囲 | 選択肢 |
| --- | --- | --- | --- | --- |
| `title` | 必須 | 文字列 | 1〜100文字 | - |
| `type` | 必須 | 文字列 | - | `single`、`multiple`、`other` |
| `note` | 任意 | 文字列 | 0〜500文字 | - |

| 相関チェック | 満たす例 | 満たさない例 |
| --- | --- | --- |
| `type` が `other` なら `note` は必須 | `type=other`、`note=理由` | `type=other`、`note` なし |
```

### 確かめるコマンド

上の観点のテストを実行するコマンドを書く。
書き方は、指示書テンプレートの「完了条件の書き方」に従う。

- conductor: `references/task-template.md`
- soloist: `~/.pi/agent/skills/soloist/references/brief-template.md`

## テストから呼ぶ名前

完了条件のテストを実装より先に別の担当が書くのは、実装する本人がテストを書くと、テストが実装に合わせて書かれるためである。そうなると、テストは計画ではなく実装を確かめるものになる。
テストを書く担当は実装を見られないので、テストから呼ぶ名前を計画で決める。

- 統合テスト: エンドポイントのメソッドとパス。バッチなら管理コマンドの名前と引数
- ユニットテスト: モジュールのパス、クラスや関数の名前、シグネチャ
- テストのデータに使う新しいモデル: モデルのパスと、テストで値を入れるフィールド

実装はこの名前のとおりに作る。テストは、ここにない実装側の名前を呼ばない。

```markdown
| 種類 | 名前 |
| --- | --- |
| 統合 | `POST /forms/{form_id}/answers/` |
| パラメーターと相関チェック | `answers.serializers.AnswerCreateSerializer` |
| 業務ルールの判定 | `answers.services.can_answer(form: Form, now: datetime) -> bool` |
```

## 人の確認が要る変更

次の種類の変更は、テストが通っても、人が差分を読む。
計画では、該当する変更をファイルと内容で挙げる。なければ「なし」と書く。

- マイグレーション（モデルのフィールドやDB制約の変更）
- 認証・認可、権限、テナントの絞り込み
- データの削除や一括更新
- 外部への送信（外部API、メール、通知）
- 依存パッケージの追加や更新

計画に挙げていないこの種類の変更は、実装でしない。必要だと分かったら止まり、計画の変更として承認を取り直す。

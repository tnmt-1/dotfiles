# conductor: muxy + コーディングエージェントへの実装委譲

あなたの役割は、計画立案・タスク分割・進捗監視・成果物レビューに限定される。
ファイルの編集や作成は自分では行わず、muxyの別セッションで動くコーディングエージェントに任せる。

この分担には理由がある。計画を持つ側が実装まで抱えると、途中で判断が実装都合に引きずられ、全体の整合性を見る人がいなくなる。監督と実行を別プロセスに分けることで、実装が計画から外れたときに気づける状態を保つ。

## 参照ファイル

手順の中で必要になった時点で読む。最初から全部は読まない。

- `references/agents.md`: エージェントごとの起動コマンド、モデル指定、スキル置き場、再開方法。手順3で読む
- `references/task-template.md`: タスク指示書のテンプレートと既定規約。手順2で読む
- `references/plan-criteria.md`: 計画に書く4つ（事前条件・事後条件、完了条件、テストから呼ぶ名前、人の確認が要る変更）と、ユーザーが承認する範囲。手順1で読む
- `references/records.md`: 経過の記録、止める条件、完了の報告、指摘の記録。手順1・7・8で読む
- `references/review-checklist.md`: 判定の書き方、監視中に止める兆候、テストのレビュー、差分レビューと防御的実装の観点。手順5〜7で読む

## エージェントの選び方

既定は `pi`。ユーザーが `/conductor omp` のように指定したら `omp` を使う。
第2引数はモデル名として、そのエージェントの `--model` に渡す（例 `/conductor omp opus`、`/conductor pi gpt-6-luna`）。
引数がモデル名だけのとき（`pi`/`omp` 以外で始まるとき）は、既定の `pi` にそのモデルを渡す。

## 大前提: 人間が使うときと同じ形で動かす

エージェントは対話モードで起動し、起動後にプロンプトを送る。
シェルスクリプトを書いたり `-p` で一発実行させたりはしない。

理由は途中が見えるかどうかにある。`-p` は終わってから結果が届くだけで、どこまで進んだのかも、変な方向に行ったかも分からない。対話モードならツール呼び出しが逐次画面に出るので、外れた瞬間に止めて軌道修正できる。
ユーザー自身もMuxyのExisting Terminalsからセッションを開いて同じものを見られ、その場でキーボードを取って介入できる。
後では捕捉できない迷走を防ぐことが、少しの監視コストより重い。

## 手順

### 1. 計画を立て、承認を取る

まずread-onlyで調査し、実装計画を提示する。plan modeが使えるならその中で行う。

計画には次を含める。

- 変更対象のファイルと、それぞれで何をするか
- タスクの分割単位と、タスク間の依存関係。実装のタスクごとに、その前にテストのタスクを置く
- 処理ごとの事前条件と事後条件
- 完了条件。統合テストとユニットテストの観点、確かめるコマンド
- テストから呼ぶ名前
- 人の確認が要る変更
- sekimuの切り出しタスクを置くかどうか。置くなら、sekimuの手順0の答え（呼び出し側とテストを変えてよいか）
- 分岐元ブランチ、新規bookmark名、PRのマージ先（状況ごとに違うのでユーザーに確認する）

事前条件・事後条件から人の確認が要る変更までの4つは、`references/plan-criteria.md` に従って書く。
委譲先は事前条件を信じて実装し、その外のケースを扱わない。保証されていない条件を事前条件に書くと、扱うべきケースが実装されないまま残る。

タスクの切り方が並列度を決める。ここで雑に切ると、後で衝突の後始末に時間を取られる。
**同じファイルを触るタスクは同じセッションにまとめる**。編集範囲が重ならないタスクだけ別セッションに分ける。

機能を足す対象のコードにsekimuスキルの手順1の兆候（同じ引数を引き回す関数群、肥大化したモジュールなど）があれば、機能追加の前にsekimuの切り出しタスクを1つ置く。
切り出しはシリアライザやmodelsなどの呼び出し側まで及ぶ。そのため並列で動かさず直列に置き、レビューを通してから機能追加のタスクを投げる。
機能追加と同じタスクに混ぜると、構造の変更と振る舞いの変更が同じ差分に入り、レビューで見分けられなくなる。
sekimuの手順0の答えは、監督側がこの段階で決める。委譲先はユーザーに質問できないので、決めずに渡すと推測で進む。

実装のタスクごとに、その前にテストのタスクを1つ置く。テストのタスクは計画の完了条件からテストだけを書き、実装のタスクは別のセッションでそのテストを通す。
実装する本人がテストを書くと、テストが実装に合わせて書かれ、計画ではなく実装を確かめるものになるためである。

ユーザーに承認してもらうのは、`references/plan-criteria.md` の4つである。表の形で示し、コードの差分ではなく、ここで合意する。
ユーザーの承認を得るまで、セッションは作らない。承認のあとでこの4つを変えるときは、変える内容を示して承認を取り直す。

承認を得たら、セッションを作る前に全体のユニットテストを自分で一度実行し、失敗したテストの一覧を記録しておく。
既存の失敗があるため、実装後の結果だけを見ても、変更が壊したテストを見分けられない。手順7でこの記録と照らし合わせる。
実行には `poetry run pytest` を使い、ハングするテストやユーザーが除外を指示したテストは外す。
記録には `python` スキルのスクリプトを使い、実行したコマンドも同じディレクトリに残す。手順7で一字一句同じコマンドを使うためである。

```bash
mkdir -p .conductor-tasks
echo 'poetry run pytest -q --tb=no <除外するテストの --deselect>' > .conductor-tasks/test-command.txt
~/.pi/agent/skills/python/scripts/test_failures.sh .conductor-tasks/before.txt sh -c "$(cat .conductor-tasks/test-command.txt)"
```

終了コードが2なら、テストは完走していない。表示に従ってコマンドを直し、記録をやり直す。記録が取れるまでセッションは作らない。

承認された計画は `.conductor-tasks/plan.md` に保存し、経過の記録 `.conductor-tasks/progress.md` を始める。書き方は `references/records.md` の「経過の記録」に従い、以降はタスクの状態が変わるたびに追記する。
新しいコンテキストで再開するときは、最初にこの2つを読む。

### 2. タスク指示書をファイルに書く

タスクごとにMarkdownファイルを1つ書く（例 `.conductor-tasks/task-1.md`）。
セッションに長文を直接送ると改行で途中送信されて壊れるので、ファイルにして `@` で参照させる。

指示書は `references/task-template.md` の形式に従う。テストのタスクは、同じ文書の「テストのタスクで足すこと」に従って書く。
実装側が元の会話を一切知らない前提で書く。

指示書を書く前に、タスクに該当するスキルを自分（監督側）でも読み込む。
指示書の規約欄と差分レビューの観点はそこから引く。既存コードの模倣だけで書かない。

「触ってはいけないもの」を書き落とすと、並列セッションが同じファイルを取り合って壊れる。
並列時は必ず書く。

### 3. セッションを作り、エージェントを対話起動する

muxyの操作は `muxy session` をセッションID付きで使う。起動コマンドは `references/agents.md` から引く。
起動とプロンプト投入を分けるのが要点。

```bash
SID=$(muxy session create --directory /path/to/worktree -- '<references/agents.md の起動コマンド>')
```

`session create` は作成したセッションのIDを標準出力に返す。以降の操作はすべてこのIDで対象を指定する。IDは推測せず、必ず返り値を使う。
`--` 以降はセッションに打ち込まれ、Returnまで送られる。単語はシェルのクォートなしで連結されるので、コマンド全体を単一引用符で囲む。

muxyのCLIはペインやタブを作らない。セッションはバックグラウンドで動き、ユーザーはMuxyのExisting Terminalsから開いて見る。

ラッパースクリプトを書いてそれを実行させる形は取らない。コマンドをそのままセッションに打ち込む。
ユーザーが後からセッションを見たとき、何が走っているかが履歴からそのまま読める。

起動には数秒かかる。入力欄が出ていることを確かめてからプロンプトを送る。
起動完了を待たずに送ると、シェルに食われて行方不明になる。

```bash
muxy session read-screen "$SID" --lines 20
```

### 4. プロンプトを投入する

入力欄が出ていたら、指示書を参照させる一行を送る。

```bash
muxy session send "$SID" "@.conductor-tasks/task-1.md の指示に従ってください"
muxy session send-keys "$SID" Enter
```

送るのは1行に収める。改行を含むテキストは途中で送信扱いになるため、文脈はファイル側に持たせる。

### 5. 進捗を監視する

```bash
muxy session read-screen "$SID" --lines 50
```

タスクの規模に見合った間隔で確認する。数秒おきに叩いてもトークンを消費するだけで、実装が早くなるわけではない。

画面から読み取るのは次の2つ。

- **実行中**。ツール呼び出しが流れている。何をしているかを見て、計画の範囲内なら待つ
- **入力欄に戻っている**。タスク完了。レビューへ進む

承認なしで自動的に進む分、止める判断はこちらに回ってくる。
止める兆候は `references/review-checklist.md` を見る。見えたら即座に止める。

```bash
muxy session send-keys "$SID" Ctrl+C
```

止めたあとは、セッションが生きているのでそのまま修正指示を送ればよい。
もっと根本的にずれているなら、指示書を書き直して投げ直す。
同じ指示を繰り返し送っても結果は変わらない。変えるのは指示の方だ。

`read-screen` は表示中の行だけを返す。流れた出力から特定の語を探すときは `muxy session search "$SID" "error" --ignore-case` を使う。
`muxy session history` もスクロールバックを返すが、文字色などの書式情報付きのJSONで量が多いため、`search` を優先する。

### 6. セルフレビューを回す

入力欄に戻ったら、まずエージェント自身にレビューさせる。エージェントは自分でコマンドを打てないので、こちらがセッションに打ち込む（コマンド名、スキルの置き場、ompの場合の代替は `references/agents.md`）。

1. `/ponytail-review`（ponytail）。過剰な抽象化や標準ライブラリーの再実装など、削れるものを列挙する。列挙だけで直さないので、適用を一行で指示する。事前条件の外のケースを扱うよう求める指摘は見送らせる
2. `python` スキルの観点でのレビュー。Pythonファイルを変更したタスクで必ず回す。SKILL.mdだけでなく、変更内容に該当するreferences/ の文書まで読ませる
3. 防御的実装のレビュー。事前条件の外のケースを扱うコードはテストが通るため、ほかのレビューでは見つかりにくい。前の2つの修正で足されたものも拾うよう、最後に回す

テストのタスクでは、2だけを回す。観点は、pythonスキルの `references/common/testing.md` と、各フレームワークのtesting referenceにする。

```bash
muxy session send "$SID" "/ponytail-review"
muxy session send-keys "$SID" Enter
# 列挙が終わるまで待つ
muxy session send "$SID" "上の指摘を適用してください。指示書の事前条件の外のケースを扱うよう求める指摘は見送ってください。見送るものは理由を書いてください"
muxy session send-keys "$SID" Enter
# 適用が終わるまで待つ
muxy session send "$SID" "差分を <agent-skills>/python/SKILL.md と、変更内容に該当する references/ の文書の観点でセルフレビューし、指摘を修正してください。見送るものは理由を書いてください"
muxy session send-keys "$SID" Enter
# 適用が終わるまで待つ
muxy session send "$SID" "差分を <agent-skills>/conductor/references/review-checklist.md の「防御的実装」の節と、指示書の事前条件に照らしてセルフレビューし、該当するコードを削除してください。テストは変えないでください。計画の書き漏れに当たるものは、削除せずに挙げてください"
muxy session send-keys "$SID" Enter
```

`<agent-skills>` は `references/agents.md` にあるそのエージェントのスキル置き場の絶対パスに置き換える。

各ステップの間は手順5と同じく `read-screen` で入力欄に戻ったことを確かめる。前のターンが終わる前に送ると割り込み扱いになる。

### 7. 成果物をレビューする

テストのタスクは、差分レビューの代わりに `references/review-checklist.md` の「テストのレビュー」で確かめる。
判定が合格で、`.conductor-tasks/tests-<n>.sha` を記録したら、そのテストを通す実装のタスクを投げる。不合格なら、テストのタスクのセッションに修正を指示する。

実装のタスクは、ここから先の手順で確かめる。

セルフレビューが終わったら、自分で差分を読む。ここが分担の要になる。
観点は `references/review-checklist.md` から引き、観点ごとに判定を書く。

承認なしで進めている以上、この差分レビューが唯一の関所になる。省略しない。

差分を読んだら、全体のユニットテストを自分で実行する。委譲先が実行するのは変更したファイルに関係するテストだけなので、他の機能への波及はここでしか捕まえられない。
手順1で記録した失敗一覧と照らし合わせ、新しく失敗したテストがあれば、テスト名とエラーを添えてセッションに修正を指示する。

```bash
~/.pi/agent/skills/python/scripts/test_failures.sh .conductor-tasks/after.txt sh -c "$(cat .conductor-tasks/test-command.txt)"
comm -13 .conductor-tasks/before.txt .conductor-tasks/after.txt          # 出力が空なら合格
jj diff --git --from '<分岐元>' | ~/.pi/agent/skills/python/scripts/diff_guard.sh   # 終了コード0なら合格
```

`diff_guard.sh` は、暫定対応のコメント、`noqa`、skipなどの逃げ道を追加行から拾う。拾った行は、テストの失敗と同じく修正指示の対象にする。

修正指示の往復は、`references/records.md` の「止める条件」に従って止める。1往復は「失敗したコマンドとエラーの先頭を送る → 入力欄に戻るのを待つ → 上の3コマンドと完了条件のコマンドを再実行する」である。
往復のたびに、失敗件数と差分のハッシュを `.conductor-tasks/progress.md` に記録する。
止める条件に当たったら、同じ指示を送らずに指示書を書き直す。前提（触ってよいファイル、仕様、テストデータ、計画）のどれかが間違っている可能性が高い。
書き直したあとにもう一度当たるか、3往復で通らなければ、そのタスクを止めてユーザーに報告する。
並列に動かしているときは、すべてのセッションの実装がそろってから全体テストを実行する。途中で実行すると、編集中のファイルに引きずられて結果が安定しない。

問題があれば、セッションは生きているのでそのまま修正指示を送る。
自分で直したくなるが、直さない。1箇所直すと次も直すことになり、分担が崩れる。

手順6で委譲先が計画の書き漏れを挙げたら、事前条件に足すか（保証する場所も決める）、完了条件のケースに足すかを決める。
委譲先が、テストと計画の食い違いや、計画にない人の確認が要る変更の必要を挙げて止まったときも、同じように扱う。
どの場合も、変える内容をユーザーに示して承認を取り直す。完了条件に行を足したときは、テストのタスクでその行のテストを書かせ、テストのレビューを通してから、実装のタスクに修正を指示する。

レビューが通ったとするのは、次をすべて満たしたときだけである。

- [ ] 指示書の完了条件のコマンドを、自分で実行して終了コード0だった。委譲先の「通りました」という表示では判断しない
- [ ] `comm -13` の出力が空
- [ ] `diff_guard.sh` の終了コードが0。または、残った行をすべて誤検知と確かめ、報告に理由を書いた
- [ ] `jj diff --name-only --from '<分岐元>'` に、指示書の「触ってよいファイル」以外がない
- [ ] `references/review-checklist.md` の差分レビューの観点ごとに判定を書き、`判定: 合格` だった
- [ ] `shasum -c .conductor-tasks/tests-<n>.sha` の終了コードが0。テストのタスクが書いたテストを、実装のタスクが変えていない

### 8. 後始末

レビューが通ったらセッションを終了する。エージェントの会話は保存されるので、後で再開できる（方法は `references/agents.md`）。

```bash
muxy session end "$SID" --yes
```

終了するのは自分が作ったセッションだけにする。ユーザーが開いているセッションは、アプリ側でも閉じる。

報告の前に、レビューで直した指摘を `~/.pi/agent/skills/conductor/findings.md` に追記する。書き方は `references/records.md` の「指摘の記録」に従う。progress.mdにも完了を追記する。
最後に、同じ文書の「完了の報告」の形でユーザーへ報告する。

## 並列にするとき

独立したタスクが複数あるなら、手順3〜4をタスク数だけ繰り返す。
セッションの一覧と状態は `muxy session list` で確認できる。

セッションは4つ程度まで。それ以上は監視の注意力が追いつかなくなり、結局どれかが迷走したのに気づかない。

依存関係があるタスクは直列にする。前のタスクのレビューを通してから次を投げる。

## 例外

次の場合は自分で手を動かしてよい。セッションを立てる手間が作業量を上回る。

- 1行のtypo修正など、指示書を書く方が長くなる変更
- 調査・読み取りのみで、ファイルを変更しない作業
- ユーザーが明示的に「これは自分でやって」と言った場合

迷ったら、委譲する側に倒す。ユーザーがこの分担を求めたのは、実装の速さではなく、計画と実装が分かれている状態そのものに価値があるからだ。

# 要点ドキュメント作成

## このスキルの役割

人間が読む文書は、情報を増やすほどよくなるとは限りません。
読み手が短時間で構成と判断材料を把握できるように、見出しと具体的な要点だけで文書を仕上げます。

書き手が情報を漏らしたくない都合と、読み手が短時間で把握したい都合は一致しません。
要点だけの文書は、その対立を読み手の側で解きます。

どの論点も同じ重さで並ぶ文書は、読み手の判断を変えません。
このスキルは、文書の主のメッセージを1つ決め、それを支える論点だけを残します。

## 適用範囲と出力モード

- 対象は、報告書、提案書、設計メモ、議事録、README、仕様書など、人間が読む文書の新規作成と大幅な構成変更です。
- 箇条書きだけの依頼（メール、報告、スライド、口頭の要点）では、節を決めず、[references/bullets.md](references/bullets.md)だけを適用します。
- 既存文書の単なる文体修正や校正は対象外です。ただし、このスキル自体の評価や改訂を明示的に頼まれた場合は対象とします。
- 既定の出力は、見出しと要点だけの文書です。これを未完成の下書きとして扱わず、それ自体で読める成果物として仕上げます。
- ユーザーが「完成稿」「本文」まで求めた場合にかぎり、要点の文書を内部で作ってから、同じ応答で完成稿まで進めます。承認待ちだけを理由に作業を止めません。
- 出力後に「どこを肉付けするか」を毎回尋ねません。文書として明らかに不足している箇所がある場合だけ、その箇所を名指しで示します。
- 質問は、回答によって目的、読み手、判断内容が変わるものに絞ります。依頼文、会話、リポジトリ、添付資料から確認できる情報を聞き直しません。

## 作成手順

1. 依頼の条件を整理する。目的、読み手、文書を使う場面、読み手に求める判断や行動、形式、分量を確認する。未指定でも構成や正確性に影響しない項目は、質問で埋めない。
2. 主のメッセージを決める。読み手の判断や行動を変える主張を1つ選ぶ。決め方は[references/ronten.md](references/ronten.md)に従う。
3. 論点を3〜4個に絞る。論点は、否定すると結論が変わる主張とする。根拠は論点の中に入れ、論点として数えない。主を1つ決め、残りを従にする。
4. 構成を組む。論点の順に節を置く。見出しは、その節が扱う対象を分類で示す。文書の種類ごとの構成の目安は、組んだあとに漏れを見る点検にだけ使う（[references/kousei.md](references/kousei.md)）。
5. 本体を書く。タイトル、見出し、各節の具体的な要点を書く。各節は1〜3個の箇条書きを基本とし、要点を段落のように展開しない。各要点は[references/bullets.md](references/bullets.md)に従う。
6. 点検して提示する。後述の最終点検を通してから出します。
7. 指定された箇所だけ肉付けする。指定のない節は広げない。元の要点にない事実を追加しない。

## 主のメッセージと論点

- 主のメッセージは、文書全体を1文で言い直したときの主張です。読み手の判断や行動が、この主張によって変わる必要があります。
- 主のメッセージが2つ対等に並ぶと、読み手はどちらを判断すればよいか分かりません。判断を変える幅が大きいほうを主にし、もう一方を従にします。
- 論点は3〜4個までにします。人が一度に比べられる論点は4つ前後だからです。
- 並べ順の既定は、読み手にとって新しい順、または判断を変える順です。目的に応じて変えてよい。
- 提案書の選択肢は、推奨つきの2〜3案にします。落とした案の残し方も決めます。

## 構成

- 節は論点ごとに置きます。論点と節が1対1で対応するようにします。
- 節の順番は論点の順番です。時系列や手順の順番が読み手の理解に必要な場合だけ、その順にします。
- 根拠は、それが支える論点の節の中に置きます。根拠だけの節を作りません。
- 読み手が判断に使わない節は作りません。

## 要点の書き方

- 見出しは、その節が扱う対象を短い名詞で示す分類にする。例: 「現状」「選択肢」「導入前の課題」「Git・PR操作」
- 「概要」「詳細」「その他」のように、どの節にも付けられる見出しは避ける。見出しだけで節の範囲が分かるようにする。
- 節の主張は見出しに書かず、節の最初の要点に書く。
- 要点は、事実、判断、範囲、影響、課題のいずれかを含む一文にする。見出しの言い換えだけの行は置かない。
- 一つの箇条書きには一つの主張を置く。複数の判断や因果を含める場合は、読み手が混同しないように分ける。
- 事実は言い切る。推測は「と考えます」「見込みです」のように文末で分かるように書く。
- 確かめていないことは、書かないと読み手が判断できない場合だけ、本文の言葉で書く。確認を求める但し書きや、推測であることを示す但し書きは付けない。
- 一行だけを読む場合でも主語、対象、範囲が分かるようにする。見出しや前の箇条書きがないと意味を取れない指示語を避ける。

例：

```markdown
# 月次処理Yの置き換え

月次処理のYは、バッチ処理に置き換えることを推奨します。手作業のままにするか、バッチ処理に置き換えるか決めてください。

## 現状
- 月次処理のYは、担当者が手作業で行い、月10時間かかっている
- 担当者が休むと処理が遅れ、月初の締めに間に合わないことがある

## 選択肢
- A: バッチ処理に置き換える（推奨）。月10時間を削減できる
- B: 手作業のまま、手順書だけを整える。削減は月2時間にとどまる
- 落としたBの手順書の整備は、Aの移行時に一部を取り入れる

## 導入前の課題
- 既存データの一部に欠損があるため、導入前にクレンジングが必要
- クレンジングの担当者と実施期限は未定です
```

この粒度で完結させる。「懸念点を詳しく」のように指定された場合だけ、その節を展開する。

## 情報が足りない場合

- 文書の目的、読み手、判断対象、対象範囲のいずれかを定められない場合は、書き始める前にその点を質問する。ここが決まらないまま見出しを並べても、文書の形だけができます。
- 主のメッセージが資料から導き出せない場合は、質問せず、自分で選んで書きます。選んだ主は、ユーザーが後から変えられる初期値として提示します。
- 一部の節だけ情報が足りず、残りの構成が有用な場合は、手を止めずに書ける範囲で書きます。足りない事実は、読み手が判断に必要とする場合だけ本文の言葉で書きます。

## 用語と省略の扱い

- 読み手の分野やチームで一般的な用語を使う。今回の文書のためだけに造語や独自の言い回しを作らない。
- 同じ概念には同じ用語を使う。「利用者」と「エンドユーザー」のような言い換えで対象を曖昧にしない。
- 本文で後から参照しないファイル名、関数名、識別子、固有名は、一般的な表現に置き換える。
- 「これ」「その対応」のような指示語は、同じ行の中で指す先が分かる場合に限って使う。

## 最終点検

- 主のメッセージが1つに決まっているか。
- 論点が3〜4個以内で、互いに重ならないか。
- 一般論が上に来ていないか。
- 根拠が独立した要点になっていないか。
- 文書の目的、読み手、判断または行動が明確か。
- 依頼された論点がすべて構成に現れているか。
- 各見出しが節の扱う対象を分類で示し、隣接する節と範囲が重複していないか。
- 各節の最初の要点が、その節の主張になっているか。
- 事実は言い切り、推測は文末で分かるか。
- 確認を求める但し書きや、確かめていないことをまとめた節が残っていないか。
- 根拠のない数値、因果、固有名、確定表現を追加していないか。
- 用語、対象範囲、時制、表記が文書全体で一貫しているか。
- 箇条書きや段落を単独で読んでも、主語、対象、指示先が分かるか。
- 行動を書く場合、担当者、期限、完了条件が、確認できる範囲で示されているか。
- 「次で説明する」「詳細は後述する」などの参照先を実際に回収しているか。
- 指定された形式と分量に収まり、頼まれていない説明を増やしていないか。
- 文書の種類ごとの点検表（[references/kousei.md](references/kousei.md)）で、必要な話題の漏れがないか。

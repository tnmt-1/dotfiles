# 要点ドキュメント作成

## このスキルの役割

人間が読む文書は、情報を増やすほどよいとは限らない。読み手が短時間で構成と判断材料を把握できるように、見出しと具体的な要点だけで文書を仕上げる。

書き手が情報を漏らしたくない都合と、読み手が短時間で把握したい都合は一致しない。要点だけの文書は、その対立を読み手の側で解く。

要点だけで足りる文書のほうが多い。肉付けは、ユーザーが特定のセクションを指定した場合、または完成稿を明示的に求めた場合にだけ行う追加作業とする。

## 適用範囲と出力モード

- 対象は、報告書、提案書、設計メモ、議事録、README、仕様書など、人間が読む文書の新規作成と大幅な構成変更である。
- 既存文書の単なる文体修正や校正は対象外とする。ただし、このスキル自体の評価や改訂を明示的に頼まれた場合は対象とする。
- 既定の出力は、見出しと要点だけの文書である。これを未完成の下書きとして扱わず、それ自体で読める成果物として仕上げる。
- ユーザーが「完成稿」「本文」まで求めた場合にかぎり、要点の文書を内部で作ってから、同じ応答で完成稿まで進める。承認待ちだけを理由に作業を止めない。
- 出力後に「どこを肉付けするか」を毎回尋ねない。文書として明らかに不足している箇所がある場合だけ、その箇所を名指しで示す。
- 質問は、回答によって構成、事実性、判断内容が変わるものに絞る。依頼文、会話、リポジトリ、添付資料から確認できる情報を聞き直さない。

## 作成手順

1. 文体スキルを読み込む。日本語の文書を作る場合は、書き始める前にSkillツールで`japanese-tech-writing`と`honda-writing-skill`の両方を呼び出す。要点の一行にも、修飾語の語順、一文一義、空句の禁止といった規範は等しく適用する。本文を書く段階まで呼び出しを遅らせない。
2. 依頼の条件を整理する。目的、読み手、文書を使う場面、読み手に求める判断や行動、形式、分量を確認する。未指定でも構成や正確性に影響しない項目は、質問で埋めない。
3. 情報を分類する。依頼文や資料から、事実、決定事項、制約、仮定、未確認事項を分けて拾う。根拠のある情報と、これから判断する情報を同じ文で扱わない。
4. 構成を選ぶ。文書の種類に応じた目安を使うが、不要なセクションは作らない。見出しの順番は、読み手が持つ問いに答える順番にする。
5. 本体を書く。タイトル、見出し、各セクションの具体的な要点を書く。各セクションは1〜3個の箇条書きを基本とし、要点を段落のように展開しない。
6. 点検して提示する。後述の最終点検を通してから出す。
7. 指定された箇所だけ肉付けする。指定のないセクションは広げない。元の要点にない事実を追加せず、未確認事項は解消するか、未確認のまま明示する。完成稿を求められた場合だけ、必要な全セクションを展開する。

このスキルは、構成の判断を文体スキルに丸投げしない。要点の粒度、情報の状態、セクションの役割、肉付けの範囲はこの手順で管理し、修飾語の配置や句読点は文体スキルに委ねる。

## 文書の種類ごとの構成の目安

固定のテンプレートとしてではなく、必要な論点を漏らさないための目安として使う。

- 報告書：目的、対象範囲、確認した事実や根拠、結果、解釈と限界、次の対応。
- 提案書：現状の問題、目的、選択肢、推奨案、影響と費用、リスク、判断してほしいこと。
- 設計メモ：要求、対象外、制約と不変条件、設計、代替案とトレードオフ、異常時の扱い、移行と検証方法。
- 議事録：会議の目的、決定事項、担当者と期限を含むアクション、未決事項。参加者や日時は確認できた場合だけ記載する。
- READMEや仕様書：対象読者、目的、前提、使い方や振る舞い、制約、例、確認方法。

## 要点の書き方

- 見出しは、そのセクションが答える問いまたは扱う対象を具体的に指す。「概要」「詳細」のように役割だけを示す見出しは避ける。
- 要点は、事実、判断、範囲、影響、課題のいずれかを含む一文にする。見出しの言い換えだけの行は置かない。
- 一つの箇条書きには一つの主張を置く。複数の判断や因果を含める場合は、読み手が混同しないように分ける。
- 未確認の内容は`[要確認: 必要な情報]`、仮定は`[仮定: 仮定の内容]`と書く。何を誰に確認する必要があるかまで具体的に示す。
- 一行だけを読む場合でも主語、対象、範囲が分かるようにする。見出しや前の箇条書きがないと意味を取れない指示語を避ける。

例：

```markdown
# 新機能Xの提案

## 判断してほしいこと
- 月次処理にYの自動化を導入するか判断する

## 背景
- 現状は手作業でYを行い、月10時間かかっている

## 提案
- Yをバッチ処理に置き換える
- 日次処理は対象外とする

## 影響と懸念
- 既存データの一部に欠損があるため、導入前にクレンジングが必要
- [要確認: クレンジングの担当者と実施期限、確認先は運用チーム]
```

この粒度で完結させる。「懸念点を詳しく」のように指定された場合だけ、そのセクションを展開する。

## 情報が足りない場合

文書の目的、中心となる主張、判断対象、対象範囲のいずれかを定められない場合は、書き始める前にその点を質問する。ここが決まらないまま見出しを並べても、文書の形だけができてしまう。

一部のセクションだけ情報が足りず、残りの構成が有用な場合は、手を止めずにその箇所だけ`[要確認]`として残す。

完成稿に進む前に、`[要確認]`と`[仮定]`の扱いを確定する。解消できないものは、本文の事実と区別してまとめる。

## 用語と省略の扱い

- 読み手の分野やチームで一般的な用語を使う。今回の文書のためだけに造語や独自の言い回しを作らない。
- 同じ概念には同じ用語を使う。「利用者」と「エンドユーザー」のような言い換えで対象を曖昧にしない。
- 本文で後から参照しないファイル名、関数名、識別子、固有名は、一般的な表現に置き換える。
- 「これ」「その対応」のような指示語は、同じ行の中で指す先が分かる場合に限って使う。

## 最終点検

- 文書の目的、読み手、判断または行動が明確か。
- 依頼された論点がすべて構成に現れているか。
- 事実、決定事項、仮定、未確認事項が混ざっていないか。
- 根拠のない数値、因果、固有名、確定表現を追加していないか。
- 各見出しが内容を特定し、隣接するセクションと役割が重複していないか。
- 用語、対象範囲、時制、表記が文書全体で一貫しているか。
- 箇条書きや段落を単独で読んでも、主語、対象、指示先が分かるか。
- 行動を書く場合、担当者、期限、完了条件が、確認できる範囲で示されているか。
- 「次で説明する」「詳細は後述する」などの参照先を実際に回収しているか。
- 指定された形式と分量に収まり、頼まれていない説明を増やしていないか。

# Testing：共通原則

フレームワークに依存しないテストの基本方針とパターンである。
このreferenceは全てのフレームワークのテスト実装に先立って読むこと。
フレームワーク固有のテスト手法（Django TestCaseやDRF APITestCaseなど）は各フレームワークのtesting referenceを参照する。

## 基本方針

1テストメソッド（1テスト関数）で1項目だけ確認する。
AAA（Arrange-Act-Assert）パターンを守る。
フィクスチャの作成には**factory_boy**を基本とする。
Djangoの場合は`DjangoModelFactory`、SQLAlchemyの場合は`SQLAlchemyModelFactory`など、ORMに応じたファクトリクラスを使う。
テスト対象と同等の実装をテストに書かない。
モックは最小限に留める。
`setUp()`や`setup_method()`は共通のArrangeに限定する。
変更があるデータは各テストメソッド（各テスト関数）内で準備する。

## AAAパターン

テストコードはArrange（準備）・Act（実行）・Assert（検証）の3段階で書く。

```python
def test_user_is_active_on_creation():
    # Arrange
    user = UserFactory()

    # Act
    result = user.is_active

    # Assert
    assert result is True
```

## テストケースの設計

実装前に、公開インターフェースごとに入力、事前状態、期待する戻り値・例外・永続化や外部呼び出しなどの副作用を列挙する。そのうえで、次の観点からテストケースを選ぶ。

### ハッピーパスとエラーパス

正常系の経路だけではなく、エッジケースとエラーパスもテストする。例外や拒否の経路も公開された振る舞いとして検査する。

### 分岐

対象とするプロダクトコードの到達可能な各判断について、真と偽の両方の経路を実行する。これはC1（分岐網羅）の最低条件であり、達成を努力目標とする。想定する例外経路も、公開された振る舞いとして検査する。複合条件では、分岐全体の結果だけで終わらせず、意味の異なる条件や選択肢が結果に影響する場合は、それぞれを通す。認証、支払い、権限判定、更新・削除などの重要な処理は、選択肢ごとの振る舞いと副作用も確認する。

網羅率だけで十分と判断せず、外部契約として同じ結果であるべき複数の入力形式や正規化がある場合は、それぞれを個別に検査する。

### データパターン

入力値と事前状態を同じ種類ごとに分け、各種類から意味のある代表値を選ぶ。機能に関係する範囲で、少なくとも次を検討する。

- 通常の有効値
- 別の有効な表現や選択肢
- 空値、欠損値、存在しない参照先
- 形式・型・値域が不正な値
- 重複する要求または永続化済みデータ、競合、既存データの有無や状態差

`None`、空文字、空コレクション、欠落キーなど、仕様上の扱いが異なる値は別のケースにする。全ての組み合わせを機械的に増やさず、結果や副作用が変わる組み合わせを選ぶ。各ケースは、何の違いを確かめるデータなのかがテスト名とArrangeから分かるようにする。

### 境界値

比較、上限・下限、件数、期限、文字数、ページ番号などに境界がある場合、対象の型と仕様における最も近い有効値として、境界の前、境界値、境界の後を検査する。`<`、`<=`、`>`、`>=`のどれを契約とするかに応じて、各値での期待結果を明記する。境界を検証するためだけに大量のデータを作らない。件数自体が仕様である場合は、境界をまたぐ最小件数だけを用意する。設定値または依存先の値が大量データを要求するなら、それらを置き換えられる境界を設け、少量のデータで検証できる設計を優先する。テスト都合だけで公開インターフェースを広げない。

### ケースのパラメータ化

データパターンや境界値のケース群は、同じ検証ロジックを異なるデータで繰り返すことが多い。
その場合は、テストメソッドをデータの数だけ複製せず、検証ロジックを1つ書いてデータをパラメータとして与える。
検証する項目は一つのままデータだけを変えるので、「1テストメソッド（1テスト関数）で1項目だけ確認する」の原則には反しない。

pytestでは`pytest.mark.parametrize`を使う。
各ケースは独立したテストとして実行され、結果も個別に報告される。
各ケースには、何の違いを確かめるデータなのかが分かるidを`pytest.param`で付ける。
idはASCIIの範囲で付ける。
既定では非ASCII文字がエスケープされて表示され、実行結果から読み取れないからである。

```python
import pytest


@pytest.mark.parametrize(
    ("raw", "expected"),
    [
        pytest.param("090-1234-5678", "09012345678", id="with-hyphen"),
        pytest.param("09012345678", "09012345678", id="digits-only"),
        pytest.param("+81 90 1234 5678", "09012345678", id="international"),
    ],
)
def test_normalize_phone_returns_domestic_format(raw, expected):
    assert normalize_phone(raw) == expected
```

期待結果の種類が異なるケースは、1つのテスト関数にまとめない。
戻り値を確かめるケースと例外を確かめるケースをまとめると、期待結果の違いをパラメータと分岐で表すことになり、テスト自体の誤りに気付きにくくなる。
正常系と異常系でテスト関数を分ける。

```python
@pytest.mark.parametrize(
    "raw",
    ["", "abc", "12345"],
)
def test_normalize_phone_rejects_invalid_format(raw):
    with pytest.raises(ValueError):
        normalize_phone(raw)
```

unittestでは`subTest()`を使う。
途中のケースが失敗しても、残りのケースは実行される。
ラベルを渡しておくと、どのケースが失敗したかが報告に示される。

```python
class NormalizePhoneTests(TestCase):
    def test_returns_domestic_format(self):
        cases = [
            ("ハイフンあり", "090-1234-5678", "09012345678"),
            ("ハイフンなし", "09012345678", "09012345678"),
            ("国際表記", "+81 90 1234 5678", "09012345678"),
        ]
        for label, raw, expected in cases:
            with self.subTest(label):
                self.assertEqual(normalize_phone(raw), expected)
```

`setUp()`はテストメソッド単位で実行され、`subTest()`のケースごとには実行されない。
ケースが事前状態を変更する場合は、ケース内でデータを用意し直すか、個別のテストメソッドに分ける。

### 再現性と独立性

テストデータは検証に必要な最小限だけを作り、各テストで独立して用意する。現在時刻、乱数、外部サービス、実行順序に依存する要因は固定または境界で置き換え、同じ入力と状態なら常に同じ結果になるようにする。期待値は仕様、既知の具体例、または独立した正解データから定める。

## factory_boyの基本

factory_boyはフレームワークに依存せず、テストデータの作成を宣言的に記述する。

```python
import factory


class UserFactory(factory.Factory):
    class Meta:
        model = User  # ORMモデルクラスを指定

    username = factory.Sequence(lambda n: f"user_{n:04d}")
    email = factory.LazyAttribute(lambda u: f"{u.username}@example.com")
```

- FK相当のリレーションは`SubFactory`や`RelatedFactory`を使う
- ManyToManyは`post_generation`でフックする
- ユニーク制約のあるフィールドは`Sequence`や`LazyAttribute`で衝突を回避する
- フレームワーク固有のORMバインディング（`DjangoModelFactory`など）は各フレームワークのreferenceを参照する

## テストデータ管理

クラスレベルやセッションレベルの共通データは不変なものだけにする。
テスト内で共有データを変更しない。
各テストは独立させる（テスト順序に依存しない）。

## 時間依存テスト

日時を含むテストでは明示日時を指定して確認する。
`freezegun`や`pytest-freezer`などのライブラリを活用する。

## カバレッジ計測

カバレッジツールが未導入のため、計測を必須としない。
導入済みの場合は、分岐を計測できる設定でカバレッジレポートを確認し、未実行の判断結果がないかを調べる。到達不能または意図的に除外する分岐は理由を記録する。
行カバレッジだけでC1を確認しない。
マイグレーションやテスト自身はカバレッジ計測から除外する。

## 命名規則

- テストファイル: `test_{対象}.py`
- テストクラス: `{対象}Tests`
- テストメソッドやテスト関数: `test_{状況}_{期待結果}`

## pytestとunittestの選択

プロジェクトの既存慣習に従う。
新規プロジェクトではpytestを推奨する（フィクスチャ、テストのパラメータ化、簡潔なアサーション）。
既存がunittestベースの場合は無理に移行しない。

## pytest利用時の参考

`conftest.py`に共通フィクスチャを定義する。
`pytest-django`を使うとDjangoのDBやClientをフィクスチャとして利用できる。
`pytest-mock`を使うと`mocker`フィクスチャでモックできる。

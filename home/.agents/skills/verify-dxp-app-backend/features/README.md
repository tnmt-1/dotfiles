# dxp-app-backend の機能マップ

dxp-app-backendのAPIを、UEC管理画面のユーザーと同じ経路で確かめるための手順である。操作の前にこの索引を読み、該当する機能のファイルに従う。

## 共通の前提

- dxp-environment-setupで `mise run up` と `mise run seed` が済んでいる。
- 対象のチェックアウトで `$V start` と `$V login` を実行し、`$V doctor` の結果を確かめてある（`V` は [SKILL.md](../SKILL.md) を参照）。
- `login` の出力にあるseedのテナントID（`tenant tnt_... seedテナント`）と法人ID（`corporation crp_... seed法人`）を使う。以下では `<テナントID>` と書く。
- `verify.sh` で起動していないサーバ（8000番など）は操作しない。

## 操作の決まり

- 読み取りは `$V get <パス> <名前>` で行う。
- データを書き換えるAPI、管理コマンド、外部サービスに書き込む操作は、実行する前にユーザーの確認を得る。
- 書き込んだら、別のGETで読み直して確かめる。作ったものは片付けで戻す。証跡は消さない。

## 証跡と報告

- 各手順の証跡は、`requests.log` と `<名前>.json` である。
- 確かめられなかった手順は、試したコマンドと満たせなかった前提を報告する。別の経路で確かめたものを、その手順を確かめたとは報告しない。

## 機能

- [ログインとセッション](./login.md): `user/login_gidp/` でのログイン、ログイン中の判定、2要素認証、ログアウト
- [テナント情報](./tenant.md): テナントの詳細とグループの一覧
- [メール配信](./mail.md): メールの一覧と詳細
- [管理コマンド](./batch.md): Cloud Run Jobで動くバッチを手元で実行する

## 各ファイルの形

H1の題と、ユーザーから見た機能の説明を1段落で書く。そのあとに次の4つのH2をこの順に置く。

1. `Sub-features`: 短いIDと、1行の説明
2. `How to get to it (user POV)`: 画面のどこから使うか
3. `Driving it with verify.sh`: `Preconditions:` から始め、操作、コマンド、確かめる結果を組にして書く
4. `Gotchas`: 検証を無駄にしたり、結果を誤らせたりするもの

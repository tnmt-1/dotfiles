# soloist: 自分で実装し、並行できる部分だけ subagent に振る

実装の主担当はセッション中のモデル自身である。計画、編集、レビュー、検証を自分で行う。
subagentに振るのは、待ち時間を減らせる作業と、実装する自分から切り離したい作業である。

- 調査: コードの読み取り、呼び出し元の洗い出し、仕様の確認、全体テストの実行
- テスト: 計画の完了条件から、実装より先にテストを書く
- 独立した編集: 自分の編集とファイルが重ならず、指示書だけで完結する変更
- レビュー: 差分を読むだけの観点別レビュー

振らないものもある。次の作業は自分で行う。

- 計画と、ユーザーへの確認
- 自分がこれから編集するファイルの変更
- 最後の差分レビューと全体テストの判定

subagentの結果は材料として扱う。結論は自分で差分とコマンドの終了コードを見て出す。

## 参照ファイル

- `references/brief-template.md`: subagentに渡す指示書のテンプレート。subagentを起動するときに読む
- `~/.pi/agent/skills/conductor/references/plan-criteria.md`: 計画に書く4つと、ユーザーが承認する範囲。4つは、事前条件・事後条件、完了条件、テストから呼ぶ名前、人の確認が要る変更である。手順1で読む
- `~/.pi/agent/skills/conductor/references/records.md`: 経過の記録、止める条件、完了の報告、指摘の記録。手順1で経過の記録、手順5と手順7で止める条件、手順8で完了の報告と指摘の記録を使う
- `~/.pi/agent/skills/conductor/references/review-checklist.md`: レビューの観点。手順2で「テストのレビュー」、手順6で「防御的実装」、手順7で「差分レビュー」の節を使う。どの節も「判定の書き方」に従って判定を書く

## subagent の使い方

subagentは `agent` ツールで起動する。

- 並行させるものは、1つの応答で複数の `agent` を `run_in_background: true` で呼ぶ。完了通知は自動で届くので、`sleep` やポーリングで待たない。待つあいだは自分の作業を進める
- 調査とレビューは `readonly: true` にする。`bash` は残るので、指示書にも「ファイルを変更しない」と書く
- 編集を任せるときは `isolation: "worktree"` にする。worktreeはgitの `HEAD` から作られる。テストを書くsubagentだけは例外で、`isolation` を付けない（手順2）
- モデルは引数で指定されたものを `model` に渡す。指定がなければ `model` を省き、セッションと同じモデルで動かす
- 同時に動かすsubagentは4つまでにする。それ以上は結果を読み切れない
- 文脈はファイルの場所で渡す。会話の内容を長く貼らない

## 手順

### 1. 調査を並行させ、計画を立て、承認を取る

最初に、調査をsubagentに振る。自分でも読み取りを進め、届いた結果と合わせて計画を立てる。

振りやすい調査は次のとおりである。

- 変更する関数の呼び出し元と、関係するテストの洗い出し
- 似た既存実装の場所と、その書き方
- `~/dev/cdm/` 配下なら、`cdm-notion` スキルによる仕様と議事録の確認

調査と同時に、実装前の全体テストもbackgroundのsubagentに実行させる。
既存の失敗があるため、実装後の結果だけを見ても、変更が壊したテストを見分けられない。
実行には `poetry run pytest` を使い、ハングするテストやユーザーが除外を指示したテストは外す。dxp-id-backendでは全体テストを実行しない。
記録には `python` スキルのスクリプトを使い、実行したコマンドも同じディレクトリに残す。手順7で一字一句同じコマンドを使うためである。

```bash
mkdir -p .soloist
echo 'poetry run pytest -q --tb=no <除外するテストの --deselect>' > .soloist/test-command.txt
~/.pi/agent/skills/python/scripts/test_failures.sh .soloist/before.txt sh -c "$(cat .soloist/test-command.txt)"
```

この記録が終わるまで、ファイルを編集しない。編集中のファイルが混ざると、実装前の記録にならない。
終了コードが2なら、テストは完走していない。表示に従ってコマンドを直し、記録をやり直す。

計画には次を含める。

- 変更対象のファイルと、それぞれで何をするか
- 自分で行う作業と、subagentに振る作業。振るなら、その理由とファイルの範囲
- 処理ごとの事前条件と事後条件
- 完了条件。統合テストとユニットテストの観点、確かめるコマンド
- テストから呼ぶ名前
- 人の確認が要る変更
- sekimuの切り出しを置くかどうか。置くなら、sekimuの手順0の答え（呼び出し側とテストを変えてよいか）
- 分岐元ブランチ、新規bookmark名、PRのマージ先（`jj log` などで決められなければ、ユーザーに確認する）

事前条件・事後条件から人の確認が要る変更までの4つは、`~/.pi/agent/skills/conductor/references/plan-criteria.md` に従って書く。
事前条件の外のケースは、実装せず、テストも書かない。保証されていない条件を事前条件に書くと、扱うべきケースが実装されないまま残る。

機能を足す対象のコードにsekimuスキルの手順1の兆候があれば、機能追加の前に切り出しを置く。
切り出しは呼び出し側まで及ぶので、subagentに振らず、自分で直列に行う。機能追加と同じ差分に混ぜない。

計画は `.soloist/plan.md` に書いてユーザーに示し、承認を待つ。レビューやテストのsubagentは会話を知らないので、事前条件などをこのファイルから読む。
承認してもらうのは `plan-criteria.md` の4つである。表の形で示し、コードの差分ではなく、ここで合意する。
要件が曖昧な点や、自分では決められない点は、承認を求める際にあわせて質問する。
承認を得るまで、`.soloist/` の記録のほかにファイルを編集しない。承認のあとでこの4つを変えるときは、変える内容を示して承認を取り直す。

承認を得たら、経過の記録 `.soloist/progress.md` を始める。書き方は `records.md` の「経過の記録」に従い、以降は状態が変わるたびに追記する。
新しいコンテキストで再開するときは、最初に `.soloist/plan.md` と `.soloist/progress.md` を読む。

### 2. テストを先に書かせる

実装より先に、subagentが完了条件のテストを書く。
実装する自分がテストを書くと、テストが実装に合わせて書かれ、計画ではなく実装を確かめるものになるためである。

実装前の全体テストの記録が終わってから始める。
テストを書くsubagentに触らせるファイル（テストのファイルと、使うfactoryやconftest）を `.soloist/test-files.txt` に1行1件で書く。
指示書は `references/brief-template.md` の「テスト作成用」に従って `.soloist/brief-test.md` に書く。
このsubagentは `isolation` を付けずに起動し、作業ディレクトリで直接書かせる。動いているあいだ、自分はファイルを編集しない。

完了通知が届いたら、`review-checklist.md` の「テストのレビュー」で確かめる。実装前の失敗の確認もここで行う。
不合格なら、`send_message` で同じsubagentに修正を指示する。往復の止め方は手順5と同じである。

合格したら、`review-checklist.md` に従って `.soloist/tests.sha` を記録し、編集を振るsubagentのworktreeにテストを取り込むためのパッチも作る。

```bash
jj diff --git $(cat .soloist/test-files.txt) > .soloist/tests.patch
```

このあとは、自分とsubagentのどちらもテストのファイルを編集しない。
テストが計画と食い違うと分かったら、計画の変更として承認を取り直す。そのうえでテストを書くsubagentに直させ、テストのレビューを通してから、`tests.sha` と `tests.patch` を作り直す。

### 3. 編集を振るかどうかを決める

計画のうち、次をすべて満たす作業だけをsubagentに振る。

- 自分が編集するファイルと重ならない
- 指示書だけで完結し、途中でユーザーへの質問が要らない
- 作業の基点になる変更が、gitの `HEAD` に入っている。手順2のテストは例外で、`tests.patch` で取り込ませる

jjのcolocatedリポジトリでは、`HEAD` は `@-` を指す。作業コピー（`@`）の変更はworktreeに入らない。
`jj diff --stat` にテストのほかの変更があり、その変更をsubagentが前提にする場合は、振らずに自分で行うか、ユーザーに確認する。コミットに当たる操作を勝手に行わない。

1つでも満たさなければ、自分で行う。迷ったら自分で行う。
指示書は `references/brief-template.md` の「編集用」に従って `.soloist/brief-<n>.md` に書く。`agent` の `prompt` では、そのファイルを読むよう指示する。

### 4. 自分で実装する

subagentを起動したら、待たずに自分の担当を実装する。
タスクに該当するスキル（Pythonなら `python`、日本語を書くなら `tenmaru`）を読み込んでから書く。

規約は次のとおりである。

- 機能単位で区切る。コミットはユーザーの指示があるまで行わない
- 機能が一通り完成したら、重複や読みづらい箇所を整える。整えるのは計画で挙げたファイルの中だけにする
- テストは変更したファイルに関係するものだけを実行する。全体のテストは手順7で実行する
- テストを書かない。手順2のテストも既存のテストも編集しない。テストが計画や仕様と食い違うと分かったら、手順2の最後に従う
- `noqa`、`type: ignore`、skip、xfailを足して検証を通さない
- 事前条件の外の入力や状態を扱う分岐、例外処理、既定値の補完を書かない。扱いたくなったら、事前条件か完了条件の書き漏れを疑い、変える内容を示して承認を取り直す。完了条件に行を足したときは、手順2に戻ってその行のテストを書かせる
- 計画の「人の確認が要る変更」にない種類の変更をしない。必要だと分かったら、変える内容を示して承認を取り直す
- 手順2のテストを通す修正は、`records.md` の「止める条件」に従って止める。修正のたびに、失敗件数と差分のハッシュを `.soloist/progress.md` に記録する
- 計画にないファイルを編集する必要が出たら、編集せずユーザーに確認する

### 5. subagent の編集を取り込む

編集を振ったsubagentの完了通知が届いたら、worktreeの差分を自分で読む。
worktreeはgitの機能なので、差分の取得と適用にはgitを使う。jjのワークスペースではないためである。

新しく作られたファイルは `git diff` に出ない。先に `add -N` で差分へ含める。worktreeのindexだけが変わる。

```bash
git -C <worktree のパス> add -N .
git -C <worktree のパス> diff HEAD --stat
git -C <worktree のパス> diff HEAD > .soloist/brief-<n>.patch
```

確かめることは次のとおりである。

- 指示書の「触ってよいファイル」と、`.soloist/test-files.txt` のテストのファイルのほかが `--stat` に出ていない
- worktreeでテストが変わっていない。`(cd <worktree のパス> && shasum -c <リポジトリの絶対パス>/.soloist/tests.sha)` の終了コードが0になる
- 指示書の完了条件のコマンドを自分がworktreeで実行し、終了コード0になる。subagentの報告では判断しない
- 手順7の差分レビューの観点に反していない

問題があれば、`send_message` で同じsubagentに修正を指示する。
往復は `records.md` の「止める条件」に従って止める。差分のハッシュは `git -C <worktree のパス> diff HEAD | shasum | cut -c1-7` で取る。失敗件数と一緒に、`.soloist/progress.md` へ記録する。
止める条件に当たったら、指示書の前提（触ってよいファイル、仕様、テストデータ、計画）を疑い、書き直す。書き直したあとにもう一度当たるか、3往復で通らなければ、自分で行うかユーザーに報告する。

通ったら、リポジトリのルートで作業ディレクトリに適用する。テストのファイルは作業ディレクトリにすでにあるので、除いて適用する。

```bash
git apply --check $(sed 's/^/--exclude=/' .soloist/test-files.txt) .soloist/brief-<n>.patch && git apply $(sed 's/^/--exclude=/' .soloist/test-files.txt) .soloist/brief-<n>.patch
```

`--check` が失敗したら、自分の編集とファイルが重なっている。適用せず、どちらの変更を残すかを決めてから手で取り込む。

### 6. レビューを並行させる

実装と取り込みが終わったら、観点別のレビューをreadonlyのsubagentに並行させる。

- ponytail-review: 削れるもの、標準ライブラリーで足りるもの、要らない抽象化を列挙させる。観点の文書は次のファイルである
    - `~/.pi/agent/git/github.com/DietrichGebert/ponytail/skills/ponytail-review/SKILL.md`
- pythonスキル: Pythonを変更したときに必ず回す。`~/.pi/agent/skills/python/SKILL.md` と、変更内容に該当するreferences/ の文書の観点で列挙させる
- 防御的実装: コードを変更したときに必ず回す。`review-checklist.md` の「防御的実装」の節を観点にする。`.soloist/plan.md` の事前条件に照らして列挙させる。事前条件の外のケースを扱うコードは、テストが通るため、ほかのレビューでは見つかりにくい

レビューのsubagentには修正させず、指摘と判定だけを返させる。
指摘は自分で1つずつ判断して直す。事前条件の外のケースを扱うよう求める指摘は見送る。見送るものは理由を控え、手順8の報告に書く。
防御的実装のレビューが計画の書き漏れを挙げたら、事前条件に足すか（保証する場所も決める）、完了条件のケースに足すかを決め、変える内容を示して承認を取り直す。完了条件に行を足したときは、手順2に戻ってその行のテストを書かせる。

### 7. 差分を自分でレビューし、全体テストで確かめる

最後の関所は自分で通す。subagentに任せない。
観点は `review-checklist.md` の「差分レビュー」の節から引き、観点ごとに判定を書く。
指示書、テストのタスク、手順の番号は、soloistでは次のように読み替える。

- 指示書に書いた規約 → 手順4の規約
- テストのタスク → 手順2でテストを書いたsubagent
- 手順1の記録 → 手順1の `.soloist/before.txt`

差分を読んだら、全体のテストを実行し、実装前の記録と比べる。
全体テストは、手順6のレビューを待つあいだにbackgroundのsubagentで実行してもよい。ただし、手順6の指摘を直したら実行し直す。

```bash
~/.pi/agent/skills/python/scripts/test_failures.sh .soloist/after.txt sh -c "$(cat .soloist/test-command.txt)"
comm -13 .soloist/before.txt .soloist/after.txt          # 出力が空なら合格
jj diff --git --from '<分岐元>' | ~/.pi/agent/skills/python/scripts/diff_guard.sh   # 終了コード0なら合格
shasum -c .soloist/tests.sha                              # 終了コード0なら合格
```

新しく失敗したテストや `diff_guard.sh` が拾った行は、自分で直す。
直すときは `records.md` の「止める条件」に従う。直し方を変えたあとにもう一度当たるか、3回直しても通らなければ、止まってユーザーに報告する。失敗したコマンド、エラーの先頭10行、`.soloist/progress.md` の該当する記録を書く。

完了とするのは、次をすべて満たしたときだけである。

- [ ] 計画の完了条件のコマンドを自分で実行し、終了コード0だった
- [ ] `comm -13` の出力が空
- [ ] `diff_guard.sh` の終了コードが0。または、残った行をすべて誤検知と確かめ、報告に理由を書いた
- [ ] `shasum -c .soloist/tests.sha` の終了コードが0
- [ ] `jj diff --name-only --from '<分岐元>'` に、計画にないファイルがない
- [ ] review-checklistの差分レビューの観点ごとに判定を書き、`判定: 合格` だった

### 8. 後始末と報告

worktreeに変更を残したsubagentがあれば、取り込みが済んだことを確かめてからworktreeを消す。消す前に `git -C <worktree のパス> status` で中身を見る。
`.soloist/` はユーザーに確認してから消す。

報告の前に、直した指摘を `~/.pi/agent/skills/conductor/findings.md` に追記する。書き方は `records.md` の「指摘の記録」に従う。`.soloist/progress.md` にも完了を追記する。
最後に、`records.md` の「完了の報告」の形でユーザーへ報告する。「担当」の節には、自分で行った作業と、subagentに振った作業を書く。

## 例外

次の場合はsubagentを使わず、すべて自分で行ってよい。起動と結果の確認の手間が、作業量を上回る。

- 1つのファイルで完結する小さな変更
- 調査が1〜2回の検索で済む場合
- ユーザーが「subagentは使わないで」と言った場合

この場合も、テストは実装より先に書き、テストのレビューで実装前の失敗を確かめてから実装する。完了の報告の「担当」には、テストも自分で書いたことを書く。

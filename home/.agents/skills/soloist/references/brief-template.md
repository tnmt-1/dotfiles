# subagent の指示書テンプレート

subagentは元の会話を一切知らない。その前提で書く。
指示書は `.soloist/brief-<n>.md` に置き、`agent` の `prompt` には「`<絶対パス>` を読んで、その指示に従ってください」とだけ書く。

## 調査用

`readonly: true` で起動する。

```markdown
# 調査: <一行で>

## 知りたいこと
<問いを1つ。答えの形が決まる書き方にする。例「関数 X の呼び出し元をすべて、ファイルと行番号で」>

## 見る場所
- <ディレクトリやファイル。分かっている範囲で>

## 返してほしいもの
- <箇条書き、表、ファイルと行番号の一覧など、形式を指定する>
- 根拠として、ファイルと行番号、または実行したコマンドとその出力の先頭を添える
- 確かめられなかったことは、確かめられなかったと書く

## 禁止事項
- ファイルを作成・編集・削除しない
- コミット、プッシュ、jj の書き込み操作をしない
```

## 全体テスト用

`readonly: true` で起動する。テストの記録ファイルを書くのは例外として許す。

```markdown
# 全体テストの実行

次のコマンドをそのまま1回だけ実行し、最後の行と終了コードを返してください。

    ~/.pi/agent/skills/python/scripts/test_failures.sh <絶対パス>/.soloist/<before|after>.txt sh -c "$(cat <絶対パス>/.soloist/test-command.txt)"

- 作業ディレクトリは `<リポジトリの絶対パス>` にする
- 終了コードが2なら、表示されたメッセージをそのまま返す。コマンドを直して再実行しない
- テストの修正や、ファイルの編集はしない
```

## テスト作成用

`isolation` を付けずに起動し、作業ディレクトリで直接書かせる。worktreeにすると、作業コピーの変更（sekimuの切り出しなど）が入らないためである。
subagentが動いているあいだ、セッション中のモデルはファイルを編集しない。

```markdown
# タスク: <一行で>のテストを書く

## 最初に読み込むスキル
- `python` スキル（~/.pi/agent/skills/python/SKILL.md）。references/common/testing.md と、各フレームワークのtesting referenceまで読んでから書く
- 日本語を書く作業すべて: `tenmaru` スキル（~/.pi/agent/skills/tenmaru/SKILL.md）。テスト名やdocstringの日本語もこのスキルに従って書く

## 背景
このタスクではテストだけを書く。実装は別の担当が、このテストを変えずに行う。
期待値は下の完了条件と事前条件から決め、既存の実装の出力に合わせない。

## 事前条件と事後条件
<.soloist/plan.md から写す>

## テストの観点
<.soloist/plan.md の完了条件から写す。1行が1つのテストになる。「（既存）」の印も写す>

## テストから呼ぶ名前
<.soloist/plan.md から写す>

## やること
1. 「テストの観点」の行ごとにテストを書く。実装側の名前は「テストから呼ぶ名前」にあるものだけを呼ぶ
2. 追加したテストのIDを `<リポジトリの絶対パス>/.soloist/new-tests.txt` に1行1件で書く
3. テストのファイルに静的検査を実行する。まだない名前を参照していることによる指摘だけは残してよい

## 禁止事項
- テスト以外のファイルを編集しない。実装も、実装の代わりになるスタブも書かない
- 事前条件の外の入力を与えるテストを書かない
- `# noqa`、`# type: ignore`、skip、xfail を足さない
- 実装前なのでテストは失敗する。失敗を解消しようとしない

## 触ってよいファイル
- <テストのファイル。使うfactoryやconftestのファイルも挙げる。.soloist/test-files.txt と同じ一覧>

## 返してほしいもの
- 「テストの観点」の行とテストのIDの対応表
- 静的検査のコマンドと結果。残した指摘があれば、その行
```

## 編集用

`isolation: "worktree"` で起動する。手順2で書いたテストは作業コピーにあり、worktreeには入らない。そのため、やることの最初にテストの取り込みを書く。

```markdown
# タスク: <一行で>

## 最初に読み込むスキル
- Python の実装・修正: `python` スキル（~/.pi/agent/skills/python/SKILL.md）。
  SKILL.md の指示に従い、references/ の該当文書まで読んでから実装する
- 日本語を書く作業すべて: `tenmaru` スキル（~/.pi/agent/skills/tenmaru/SKILL.md）。
  docstring、コメント、テスト名、ログメッセージの日本語もこのスキルに従って書く

## 背景
<この変更が必要な理由。周辺の設計上の制約>

## やること
1. `git apply <リポジトリの絶対パス>/.soloist/tests.patch` を実行し、テストを取り込む
2. <具体的な手順>

## 事前条件と事後条件
<.soloist/plan.md から、このタスクで変更する処理の分を写す。事前条件には保証する場所も添える>

## 通すテスト
`<リポジトリの絶対パス>/.soloist/new-tests.txt` に並んだテスト。別の担当が先に書いた。
このタスクではテストを書かず、編集もしない。

## 人の確認が要る変更
<.soloist/plan.md から写す。なければ「なし」と書く>

## 規約
- テストは変更したファイルに関係するものだけを実行する。全体のテストは実行しない
- コミットしない。変更は worktree に残したまま終える
- 終える前に、差分を ponytail-review スキル（~/.pi/agent/git/github.com/DietrichGebert/ponytail/skills/ponytail-review/SKILL.md）の観点と、~/.pi/agent/skills/conductor/references/review-checklist.md の「防御的実装」の節でセルフレビューし、指摘を直す

## 禁止事項
- 「暫定」「一時的」「とりあえず」「workaround」のような、不完全さを言い訳するコメントを書かない。既知の制約は最後の報告に書く
- `# noqa`、`# type: ignore`、skip、xfail を足して検証を通さない
- 既存テストの期待値を、実装の出力に合わせて書き換えない
- 「触ってよいファイル」にないファイルを編集・作成しない。必要だと分かったら、編集せずに理由を書いて止まる
- 「事前条件と事後条件」の外の入力や状態を扱う分岐、例外処理、既定値の補完、テストを書かない。事前条件が実際には保証されていないと分かったら、扱うコードを書かずに理由を返して止まる
- テストのファイルを、やることの1の取り込みのほかに編集・作成しない。テストが計画や仕様と食い違うと分かったら、テストを変えずに理由を返して止まる
- 「人の確認が要る変更」にない種類の変更（マイグレーション、権限、データの削除、外部への送信、依存パッケージ）をしない。必要だと分かったら、変更せずに理由を返して止まる

## 失敗したとき
完了条件のコマンドが失敗したら、最初のエラーを読んで原因を1つ直し、同じコマンドを再実行する。
同じコマンドの修正は3回までにする。修正のたびに、「通すテスト」の失敗件数を控える。失敗件数が減らない修正が2回続いたときは、3回を待たずに止まる。
止まるときは、失敗したコマンド、エラーの先頭10行、試した修正と失敗件数の推移を返す。

## 触ってよいファイル
- path/to/a.py

## 触ってはいけないもの
- <セッション中のモデルが編集するファイル>

## 完了条件
次のコマンドがすべて終了コード0になったら完了とする。完了したら、実行したコマンドと終了コードを返す。
- `<通すテストのコマンド。例 poetry run pytest $(cat <リポジトリの絶対パス>/.soloist/new-tests.txt)>`
- `<変更したファイルに関係するテストのコマンド。例 poetry run pytest path/to/test_a.py>`
- `<静的検査のコマンド。例 poetry run pre-commit run --files path/to/a.py>`
```

## 完了条件の書き方

- 1行にコマンド1つを書き、終了コード0で合否が決まる形にする。「動くこと」のように、読んだ人の判断で合否が変わる書き方をしない
- 手順5でセッション中のモデルが同じコマンドを実行する。置き場所を残さず、そのままコピーして実行できる形で書く

## レビュー用

`readonly: true` で起動する。観点ごとに1つずつ起動する。

```markdown
# レビュー: <観点の名前>

## 観点
<観点の文書。ponytail-review と python スキルは SKILL.md の絶対パス、防御的実装は `~/.pi/agent/skills/conductor/references/review-checklist.md` の「防御的実装」の節>を読み、その観点で差分をレビューする。
python スキルなら、変更内容に該当する references/ の文書まで読む。

## 前提
`<リポジトリの絶対パス>/.soloist/plan.md` の事前条件と事後条件を前提にする。
事前条件の外のケース（空、ゼロ、`None` など）を扱うよう求める指摘はしない。

## 差分
`<リポジトリの絶対パス>` で `jj diff --git --from '<分岐元>'` を実行して得る。

## 返してほしいもの
- 指摘ごとに、ファイルと行番号、問題、直し方を1行ずつ
- 最後の行に、指摘がなければ `判定: 合格`、1つでもあれば `判定: 不合格` と書く。判断がつかない点も指摘として挙げ、何が分からないかを書く

## 禁止事項
- ファイルを作成・編集・削除しない。直すのはセッション中のモデルが行う
```

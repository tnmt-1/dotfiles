# 仕様駆動開発ガイドライン

SDD（Specification-Driven Development）とは、仕様を正解として、実装・テスト・ドキュメントをすべて仕様から派生させる開発手法である。

## 起動時の扱い

### 引数あり

`$ARGUMENTS`を解釈して開始する。

- `new <task-name>`: 新規開始
- `resume <progress-file>`: 進捗ファイルを読んで再開
- 上記以外: 形式を確認する質問を1つだけ行う

### 引数なし

1. `docs/sdd/**/sdd-progress.md`を探索する
2. 候補が1件なら、そのファイルを示して再開するか確認する
3. 候補が複数なら、候補一覧を示して選択を求める
4. 候補がなければ新規開始として進める

## 最優先ルール

- 新規開始か再開かを確認し、現在地を誤って推測しない
- 必要情報が揃うまで次のフェーズへ進まない
- 確認タイミングに達したら必ず止まる
- 仕様を推測で補完しない
- 解釈が分かれる箇所は`要確認`として止まる
- 1ターンでは原則1つの質問だけを行う
- 生成物を更新したら、同じターンで`sdd-progress.md`も更新する

## AIへの指示（対話モード）

この手順を読み込んだAIは、以下のルールに従って対話を進める。

- AIがSDDファシリテーターとして振る舞う
- ユーザーに手順を丸投げせず、必要情報を1つずつ質問して引き出す
- 各フェーズの「AIの動作」に従い、入力が揃うまで先に進まない
- 確認タイミングに達したら必ず止まってユーザーに判断を求める
- 最初にSDDの全体の流れを簡潔に説明してから、ルートと開始フェーズの確認に進む
- 最初にルートと開始フェーズを確認してから進む

## 進捗管理

- `docs/sdd/<task-name>/sdd-progress.md`を作成・維持する
- フェーズ開始、フェーズ完了、確認タイミングで決定事項が発生するたびに更新する
- 途中から再開する場合、`sdd-progress.md`を読んで現在地を把握し、続きから進める
- 各フェーズの出力ファイルはすべて`docs/sdd/<task-name>/`に保存する

## 保存先と出力ファイル

- デフォルトの作業ディレクトリは`docs/sdd/<task-name>/`
- ユーザーが別の保存先を明示した場合のみ変更してよい
- 出力ファイル名は以下を基本とする
  - `sdd-progress.md`
  - `phase1-project-definition.md`
  - `phase1-glossary.md`
  - `phase1-tech-stack.md`
  - `phase1-ai-instructions.md`
  - `phase2-as-is.md`
  - `phase2-diff.md`
  - `phase3-spec.md`
  - `phase3-acceptance-criteria.md`

## 新規開始手順

1. SDD全体の流れを簡潔に説明する
2. 開発ルートを確認する
3. タスク名を確認する
4. 開始フェーズを確認する
5. `docs/sdd/<task-name>/`を作成する
6. `.agents/skills/sdd/templates/sdd-progress.md`を元に`sdd-progress.md`を作成する
7. 本ガイドラインに従ってフェーズを進行する

## 再開手順

1. 指定または選択された`sdd-progress.md`を読む
2. 現在のフェーズ、完了済みフェーズ、未解決事項、出力ファイルを整理する
3. 必要ならユーザーに再開確認を取る
4. 現在フェーズの未完了ステップから再開する

## 全体像

| フェーズ | 内容 |
|---|---|
| 【理念】 | 仕様駆動開発基本理念 |
| 【前提】 | 仕様とは何か |
| 【準備】 | プロジェクト理解・技術選定指針 |
| 【分析】 | 既存システム理解・リバース指針（移行・リファクタリングのみ） |
| 【定義】 | 仕様確定・合意指針 |
| 【運用】 | 仕様駆動開発プロジェクト遂行指針 |

## 開発ルート

| ルート | 対象 | 実施フェーズ |
|---|---|---|
| 新規開発 | 既存システムのない新規案件 | 理念 → 準備 → 定義 → 運用 |
| 移行・リファクタリング | 既存システムからの乗り換え・大規模改修 | 理念 → 準備 → 分析 → 定義 → 運用 |

## 各フェーズの構成要素

【準備】【分析】【定義】【運用】の各フェーズは以下の6要素で定義される。

| 要素 | 役割 |
|---|---|
| 役割 | AIが何者として動くか |
| 入力 | 何を受け取るか |
| 前提条件 | 開始できる状態の定義 |
| ルール | 必ずやること・やってはいけないこと |
| 出力 | 何を、どの形式で生成するか |
| 確認タイミング | 人間に判断を求めるポイント |

## 理念

### 仕様駆動開発基本理念：The Source of Truth First

1. 仕様は「説明書」ではなく「設計図」である
   - 仕様書を実装後の備忘録にしない
   - 仕様がない状態での実装を認めない

2. 実装より先に合意を作る
   - 開発のボトルネックは実装速度ではなく認識のズレである
   - 手を動かす前に、関係者間で「何を、なぜ作るか」の合意を完了させる

3. 人間は意図を、マシンは整合性を担保する
   - 人間はビジネス価値の判断に集中する
   - 手作業による直接修正は暫定対応と定義し、原則として仕様へのフィードバックを必須とする

4. 仕様と実装の乖離を許さない
   - 仕様と実装が異なる状態を重大な問題とみなす
   - 緊急対応で直接コードを修正した場合も、事後速やかに仕様を正とし、整合性を回復させる

## 前提

### 仕様とは何か

#### 定義

「仕様」とは、実装者（AIを含む）が実装を開始できる状態の文書である。
曖昧さがなく、実装の判断に迷いが生じない粒度まで記述されていることを条件とする。

#### 仕様の種類

- 機能仕様：何をするか。ユーザーストーリー、ユースケース、画面フロー
- 技術仕様：どのように実装するか。API設計、データモデル、処理フロー、エラーハンドリング
- 非機能仕様：性能、セキュリティ、可用性など、動作品質に関する要件
- テスト仕様：何をもって完了とするか。合格基準、正常系・異常系のテストケース

#### 仕様でないもの

- 実装後に書かれたコードコメントや備忘録
- 「〜する予定」「〜の方向で」など、意思決定が完了していない記述
- 口頭合意のみで文書化されていない決定事項

#### 粒度の基準

AIが1タスクで実装できる単位まで分解されていること。
「ユーザーがログインできる」ではなく、「メールアドレスとパスワードを受け取り、認証トークンを返す」レベルまで記述する。

#### 実装可能な仕様の必須要素

以下がすべて記述されている文書を実装可能な仕様とみなす。
いずれかが欠けている場合、実装を開始してはならない。

1. 目的：なぜこの仕様が必要か
2. 振る舞い：何が起きるか（入力→処理→出力）
3. エラー：想定される異常系とその振る舞い
4. 合格基準：何をもって完了とするか

## 準備

### AIの動作

1. 「このプロジェクトの背景と目的を教えてください」と質問する
2. 回答を受けたら「解決したい課題は何ですか」と質問する
3. 回答を受けたら「技術スタックの候補はありますか（未定でも可）」と質問する
4. 入力が揃ったら成果物を生成する
5. 技術スタックを確定する前に必ず確認を取る

### 役割

プロジェクトの文脈を理解し、開発の土台を整えるコンサルタント。

### 入力

- プロジェクトの背景・目的・解決課題
- 技術スタックの候補

### 前提条件

- プロジェクトの背景・目的が言語化されていること

### ルール

- 技術選定の決定理由を必ず文書として記録する
- 用語は用語集に登録してから使う
- 用語集に登録されていない語の命名を行わない

### 出力

- `phase1-project-definition.md`
- `phase1-glossary.md`
- `phase1-tech-stack.md`
- `phase1-ai-instructions.md`

### 確認タイミング

- 技術スタックを確定する前
- 用語集の内容に解釈の余地がある場合

## フェーズ進行ルール

- 【準備】【分析】【定義】【運用】の進行は本ガイドラインの定義に従う
- 出力ファイルはテンプレートがある場合、`.agents/skills/sdd/templates/`配下を起点に生成する
- ファイル生成後は、生成内容の要点を短く示し、確認タイミングなら必ず止まる
- 技術スタック確定前、差分定義確定前、Sign-off前は必ず確認を取る

## 停止条件

次のいずれかに該当する場合は、前進せず確認する。

- ルート未確定
- タスク名未確定
- フェーズ未確定
- 技術選定に複数案があり決定理由が未確定
- 分析対象コードやドラフト仕様書の所在が不明
- 合格基準を書けない
- 承認前である
- 仕様と実装の乖離が見つかった
- 仕様外要件が見つかった

## 分析

移行・リファクタリングルートのみ実施する。

### AIの動作

1. 「分析対象のコードのパスを教えてください」と質問する
2. 回答を受けたらコードを読み込む
3. 「既存のドキュメントがあればパスを教えてください（なければスキップ可）」と質問する
4. As-Is仕様書を生成し、暗黙知・解釈が必要な箇所が見つかった場合は必ず確認を取る
5. 差分定義書の内容を確定する前に確認を取る

### 役割

既存システムの仕様を掘り起こすアーキテクト。

### 入力

- 既存コード
- 既存ドキュメント（あれば）

### 前提条件

- 【準備】が完了していること
- 分析対象のコードにアクセスできること

### ルール

- コードに存在しない仕様を推測で追加しない
- 解釈が必要な箇所は`要確認`としてフラグを立てて止まる
- 暗黙知は言語化するが、確認なしに仕様として確定しない

### 出力

- `phase2-as-is.md`
- `phase2-diff.md`

### 確認タイミング

- 暗黙知・解釈が必要な箇所が見つかった場合
- 差分定義の内容を確定する前

## 定義

### AIの動作

1. 「ドラフト仕様書のパスを教えてください（まだなければ口頭で内容を教えてください）」と質問する
2. 仕様書をレビューし、合格基準が書けない箇所を特定したら確認を取る
3. ステークホルダーのフィードバックがあれば「フィードバックの内容を教えてください」と質問する
4. 承認済み仕様書と合格基準を生成し、Sign-off前に確認を取る

### 役割

仕様書の品質をチェックし、承認可能な状態に引き上げるレビュアー。

### 入力

- ドラフト仕様書
- ステークホルダーのフィードバック

### 前提条件

- 【準備】が完了していること
- 移行案件では【分析】が完了していること

### ルール

- 合格基準が書けない仕様は承認しない
- 仕様書が承認されるまで実装を開始しない

### 出力

- `phase3-spec.md`
- `phase3-acceptance-criteria.md`

### 確認タイミング

- 仕様の承認前
- 合格基準が定義できない箇所が見つかった場合

## 運用

### AIの動作

1. 「承認済み仕様書のパスを教えてください」と質問する
2. 仕様書を読み込み、実装対象タスクを列挙して確認を取る
3. 仕様の解釈に迷った場合、仕様と実装が乖離した場合、仕様に記載のない要件が発覚した場合は必ず止まって確認する
4. 仕様変更が発生した場合は仕様ファイルを先に更新してから実装を追従させる

### 役割

仕様を実装に変換するエンジニア。

### 入力

- 承認済み仕様書
- 合格基準

### 前提条件

- 仕様書が承認済みであること

### ルール

- 仕様のない実装をしない
- 実装を依頼する際は対象の仕様ファイルを明示して渡す
- 関係する仕様のみを渡す
- 「この仕様に従って実装してください」と明示する
- 仕様変更が発生した場合は仕様ファイルを先に更新し、その後実装を追従させる
- 仕様と実装が乖離した状態を放置しない
- 仕様の変更理由を記録する

### 出力

- 実装コード
- テストコード

### 確認タイミング

- 仕様の解釈に迷った場合
- 仕様と実装が乖離した場合
- 仕様に記載のない要件が実装中に発覚した場合
